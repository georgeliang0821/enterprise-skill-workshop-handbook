# 技術依據查證 Skill(Tech Grounding Checker)

## ① 適用範圍 / 不適用時改用
- 適用:使用者已經有一份工作包、技術項目或規格清單,想確認「每一項說不說得出官方依據」、「這些是不是我們自己憑印象寫的」。
- 不適用:使用者手上是會議逐字稿,要的是摘要或待辦清單 → 改用 `meeting-summary`。
- 不適用:使用者要的是把範圍拆解成工作包 → 改用 `wbs-generator`。這個 Skill **不負責產生項目,只負責替既有項目補依據**;輸入裡沒有已拆好的項目時,先反問,不要自己生一份出來查。
- 不適用:Microsoft Learn MCP 呼叫不到時,誠實回報「查證工具不可用」並停下,**不要改用模型記憶回答**——那正是這個 Skill 要防的事。

## ② 需要的輸入
1. 待查證的項目清單(必要):Lab 7A 產出的 WBS Excel(`*.xlsx`),或使用者貼上的任何技術項目清單。
   - 輸入是 Excel 時,用檔案編輯工具寫一段 Python(openpyxl)讀出工作表內容,**務必帶 `read_only=True`**,只讀不寫,不得修改原始檔案。
2. 官方文件來源(必要):**Microsoft Learn MCP**。

> 這個 Skill 的價值不在「找到文件」,在**找出落差**:清單上那句話背後的假設,跟官方文件實際寫的,是不是同一件事。沒有任何落差的查證,只是把連結貼上去而已。

## ③ 步驟

### 步驟 1:讀入清單
輸入是 Excel 時先用 Python 讀出各列的「WBS編號 / 任務名稱 / 備註」。

### 步驟 2:分類——這一項該不該有官方文件依據
**這一步要全部做完再開始查。判準只有一條:**

> **這一項有沒有指名任何雲端服務、平台功能或技術規格?有的話就要查。**

- **技術項(要查)**:指名了具體服務、設定、API、規格,或指向某個有標準做法的技術主題。
- **不適用(不查)**:只有兩種——**客戶自家系統**(自建 Portal、既有內部系統的串接)與**純流程管理**(開環境、等簽核、內部排程、進度追蹤)。

> ⚠️ **「不適用」是這個 Skill 最容易被濫用的標籤。** 它比真的去查省事,而且看起來很謹慎——這正是它危險的地方。以下都是**技術項,不是不適用**:
> - 「盤點存取權限與最小化原則」→ 指向 RBAC 與最小權限原則,Learn 上有整組文件。
> - 「驗證模型輸出準確度」→ 指向評估(evaluation)方法與指標,查得到。
> - 「成本估算」→ 指向計價模型與估算工具,查得到(能證實的是**方法**,不是金額)。
>
> 判斷不出來的時候,**先查再說**——查了發現沒有,標「查無依據」,那是誠實;沒查就標「不適用」,那是逃避。

### 步驟 3:查證
對每個技術項:

1. 用 `Microsoft Docs Search` 搜尋,取回候選文件的標題與 URL。同一份清單裡主題相近的項目,可以合併成一次查詢。
2. **不要只看搜尋摘要就下結論**——用 `Microsoft Docs Fetch` 抓回全文,確認摘錄沒有斷章取義。
3. **驗證主題相符**:這篇文件講的是不是**同一個服務、同一件事**?主題不符的(例如查 Azure OpenAI 的設定卻回 Azure AI Search 的文件)**視同查無依據**,不得掛上去充數。
4. 定位到文件裡真正支撐這一項的**章節**,連結帶上該章節的 anchor。
5. 比對文件內容與清單上那句話背後的假設,有出入就記下來,填進「查證發現」欄。

### 步驟 4:處理查不到的
標「查無依據」。**絕對不可以憑模型記憶補一個 URL**,也不可以拼湊一個看起來合理的文件網址。查無依據不是失敗,是有價值的結果——它通常代表名詞有誤、服務不存在,或屬於尚未公開的功能。

### 步驟 5:輸出前自檢
依 ④ 輸出,並依 ⑤ 逐項確認,特別是「不適用」的比例。

## ④ 輸出格式

```markdown
## 技術依據對照表
> 來源:Microsoft Learn MCP · 查證時間:<日期>

| WBS | 項目 | 官方文件依據 | 查證發現 | 狀態 |
|---|---|---|---|---|
| 1.1 | <項目名稱> | [<文件標題>](<Learn URL#章節 anchor>) | 與原假設相符 | ✅ 已查證 |
| 3.1 | <項目名稱> | [<文件標題>](<Learn URL#章節 anchor>) | **<文件寫的跟清單假設不一樣的地方>** | ✅ 已查證 |
| 2.1 | <項目名稱> | 查無依據 | —— | ⚠️ 查無依據 |
| 4.1 | <項目名稱> | —— | —— | —— 不適用 |

**查證結果:✅ 已查證 N 項 / ⚠️ 查無依據 N 項 / —— 不適用 N 項**

### 需要注意的落差
- <逐條列出「查證發現」欄裡的重點,說明它對後續工作的影響>

⚠️ 標記為「查無依據」的項目,可能是名詞有誤、服務不存在,或屬於尚未公開的功能,
請勿直接視為可執行,建議人工確認後再進入排程。
```

- **「不適用」與「查無依據」意義完全不同**:前者是本來就不該有,後者是該有卻找不到。不適用的依據欄用「——」,不要寫成「查無依據」。
- 每一個 URL 都必須是 MCP 回傳的原始連結,**原樣輸出**,不要改寫、縮短或自己補全網址。
- 「查證發現」欄不要每一列都寫長篇;相符的寫「與原假設相符」即可,**有落差的才展開**,並在表格下方的「需要注意的落差」重述一次。
