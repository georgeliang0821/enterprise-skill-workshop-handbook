會議紀錄:AI Meeting Intelligence Portal 導入評估會議
日期:2026-07-08(週三)10:00-10:45
與會人員:
- Host(PM,會議主持人)
- David(解決方案架構師)
- Mary(財務 / 採購窗口)
- George(資安與合規窗口)

---

Host:各位早安,今天這場會議大概 45 分鐘,目的是把「AI Meeting Intelligence Portal」這個內部工具的技術路線定案。我們上週已經看過三個選項:自建開源模型、用某雲的通用 LLM API,還有 Azure OpenAI。David,先請你講一下架構面的評估。

David:好。三個選項裡,自建開源模型雖然長期授權成本低,但我們沒有足夠的 GPU 資源,且維運團隊要額外投入至少兩個人力,時程上不現實。通用 LLM API 那個廠商的合約條款我看過,資料使用權限寫得不夠清楚,George 之後應該會提到這塊。相對來說,Azure OpenAI 因為我們本來就是 Azure 客戶,可以直接沿用現有的 Entra ID 身分驗證,也比較容易跟我們既有的 M365 環境整合,架構複雜度最低。

Host:了解,那從財務角度呢?Mary。

Mary:我這邊初步抓的是 token 用量成本。如果照現在預估的會議量,一個月大概是幾千次摘要請求,用 GPT-4 等級的模型算下來,token cost 會是這個專案目前最大的變動成本項目,如果之後會議量成長,這個數字會線性往上跳,這點我會列為財務面的風險項目,需要之後每個月追蹤。

Host:這個我們列進風險清單。George,資安這邊呢?

George:我這邊主要關注兩件事。第一是剛剛 David 提到的資料使用權限,通用 LLM API 那家的條款我確認過,沒有明確承諺不會拿客戶資料做模型訓練,這對我們處理內部會議紀錄來說風險偏高。第二是資料落地,也就是 Data Residency——我們的會議紀錄裡有客戶名稱、報價這些敏感資訊,如果模型服務的資料處理地點不在我們可以掌控的區域,會有合規疑慮。Azure OpenAI 至少可以指定資源部署的區域,這點會比較好處理,但我還是要正式跑一次資安需求確認流程,不能只憑口頭結論。

Host:所以資料落地(Data Residency)也要列進風險清單。整體聽下來,大家的傾向都是 Azure OpenAI,我們可以做個決議嗎?

David:同意,我覺得 Azure OpenAI 是目前最務實的選擇。

Mary:財務面沒有反對意見,只是 token cost 要持續追蹤。

George:資安面初步沒有反對,但正式的資安需求確認我還是要走一輪。

Host:好,那我們今天的決議就是:第一,採用 Azure OpenAI 作為這個 Portal 的模型服務;第二,下週開始進行 PoC,先驗證摘要與待辦事項抽取的準確度。David,PoC 的架構設計麻煩你這週五前先出一版草稿。

David:沒問題,我這週五前會把 PoC 架構設計初稿寄出來,包含 Azure OpenAI 資源配置和跟現有 Portal 前端的串接方式。

Host:Mary,成本評估這邊麻煩你比對一下不同用量情境下的月費預估,下週會議前給大家看一下。

Mary:好的,我這邊會做出三個情境(低/中/高用量)的成本評估,下週會議前寄給大家。

Host:George,資安需求確認麻煩你這邊主導,包含剛才提到的資料落地跟存取權限盤點。

George:了解,我會確認資安需求,重點會放在資料落地地區設定跟權限最小化原則,大概下週三前可以有初步結論。

Host:另外補充一點,這個 PoC 之後如果驗證順利,中期我們有評估過,未來這個 Portal 是否要跟 SAP 系統做整合,例如把會議裡提到的採購相關決議自動同步到 SAP 的請購流程,這個目前先不排進 PoC 範圍,但先記錄下來,之後規劃第二階段時會再拿出來討論。

Mary:對,如果之後要接 SAP,採購那條線的成本評估邏輯可能要重算,先備註起來。

Host:好,今天先到這邊。總結一下:專案進度正常,決議是採用 Azure OpenAI、下週進行 PoC;待辦事項 David 負責 PoC 架構設計、Mary 負責成本評估、George 負責資安需求確認;風險項目是 Token Cost 跟 Data Residency,大家追蹤一下。謝謝各位。
