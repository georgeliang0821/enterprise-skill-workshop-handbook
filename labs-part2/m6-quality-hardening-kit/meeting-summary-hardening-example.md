# 硬化案例示範:meeting-summary 的 V1 → V2 → V3

這份文件示範「品質規則怎麼從真實回饋長出來」,用的是你們上半場已經寫過的 `meeting-summary` Skill。討論時可以直接用你們自己在 Lab2 實際遇到的問題替換掉下面的假設案例。

---

## V1(上半場 Lab2 剛完成的版本)

```yaml
quality:
  - 摘要要精簡
  - 決議要正確
  - 風險要完整
```

問題:這三條規則都無法被驗證。「精簡」多短算精簡?「正確」怎麼判斷?「完整」要完整到什麼程度?這種規則放在 SKILL.md 裡,基本上等於沒有規則。

---

## V2(拿真實會議紀錄跑過一輪之後)

假設團隊實際使用後回報兩個具體問題:

1. 有一場會議裡,PM 說「我們**可以考慮**採用某方案,但還需要再確認預算」,結果被誤判成 Decisions 裡的一項——這不是拍板,是討論中。
2. 另一場會議完全沒提到任何風險,但輸出的 Risks 區塊裡出現了「時程可能延誤」——逐字稿裡根本沒人講過這句話,是模型自己推論出來的。

對應的品質規則升級:

```yaml
quality:
  - Decisions 每一項都要能在逐字稿找到「明確拍板」的語句(例如「我們決議…」「就這樣定案」),
    單純的「可以考慮」「還在討論」不算。
  - Risks 每一項都要能對應逐字稿裡具體的一句發言,不能是摘要者自己推論出來、
    逐字稿沒提到的內容;完全沒有風險時,明確寫「無」。
```

版本從 `0.1.0` → `0.2.0`(新增品質規則,輸出結構沒變,屬於 Minor 升級)。

---

## V3(累積更多真實案例後)

假設又發現:不同會議的 Decisions 有時候寫成完整句子、有時候寫成關鍵詞,團隊內部拿去做週報彙整時,格式不一致很難自動處理。這時候規則要再往「格式一致性」推進:

```yaml
quality:
  - (沿用 V2 的兩條規則)
  - Decisions 每一項固定用「動詞+受詞」的完整短句(例如「採用 Azure OpenAI」),
    不要用不完整的關鍵詞片段(例如只寫「Azure OpenAI」)。
```

版本從 `0.2.0` → `0.3.0`。

> **如果**這次連 Decisions 的輸出結構本身都要改(例如從純文字清單改成「決議內容 + 決議日期」的物件結構),那就不只是加規則,而是**改變了下游依賴的輸出格式**——這種情況要跳 Major 版本(例如 `0.x.0` → `1.0.0`),並且要主動通知所有依賴這個 Skill 輸出格式的人(例如 Portal 前端的 parser、或串接這個輸出的其他 Skill)。

---

## 討論重點(講師帶討論用)

- 每一條新規則,都能回頭指出「是哪一次真實使用中的哪一句話讓我們加了這條規則」——這是判斷一條品質規則「值不值得加」的標準,不是憑空想像「還可能會出什麼錯」。
- 版本號的升級不是儀式,是**溝通**:團隊裡其他人看到版本從 `0.2.0` 跳到 `1.0.0`,應該立刻警覺「這次可能要檢查自己有沒有依賴舊的輸出格式」。
