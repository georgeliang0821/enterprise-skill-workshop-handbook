## 填表提示

- **具體案例欄是靈魂**:要寫到「事後任何人看了都能指出是哪一次使用、哪一句話」的程度。「輸出品質不穩」不合格;「David 的『這週五前』被原樣輸出沒換算日期」合格。
- **M2a 那列的特殊性**:漂移實驗發生在 Skill 存在之前,所以它收割出來的不是「升版」,而是 v0.1.0 的**整組初始規則**(決議需拍板、日期換算、Owner 用姓名、空區塊寫「無」)——記進 CHANGELOG 的 v0.1.0 條目,讓後人知道這些規則不是憑空想的。
- **M3c 那列**:改 description 通常是 Patch(不影響邏輯或輸出結構)——但如果你當時是靠**改寫適用範圍**才修好誤觸發,那就是 Minor。判斷的依據是「下游會不會受影響」,不是改動行數。
- **M5 那列**:撞 A 的去重是新增規則(Minor);撞 C 把 `disable-model-invocation` 從 false 改 true——想一想:這改變了「使用者怎麼觸發它」的對外行為,你覺得算 Minor 還是 Major?(這題沒有標準答案,重點是你能說出你的判斷依據,並在 CHANGELOG 裡寫清楚,讓團隊其他人不會被 surprise。)

## 帶回團隊的習慣

今天的四次事故是講師設計的;回公司之後,事故是真實使用送上門的。流程一樣:

```
團隊成員回報「這次輸出怪怪的」
   → quality-rule-backlog 記一行(當下記,越具體越好)
   → 定期檢視,重複出現的升級成 SKILL.md 正式規則
   → 同步 CHANGELOG + 升版
```

`quality-rule-backlog-template.md` 就是這張收割表的日常版。
