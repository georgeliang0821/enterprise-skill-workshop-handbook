從 Prompt 到 Skill

同一句 Prompt,為什麼每個人跑出來都不一樣——以及三個 Skill 怎麼把它收斂成每次都一樣。今天一整天,我們只做一件事:把「AI Meeting Intelligence Portal」這個產品做出來。上半場結束時你手上會有:一份精簡過的 AGENTS.md、一個 prompt file、三個親手撰寫且經實測驗證的 Skill,和一張三輪 before/after 的紀錄。

📌講義設計原則

「先定終點,再把技術主題掛在功能上」——每個重要觀念,都先讓你親眼看到沒有它會出什麼事,再教解法。 上半場有兩次刻意安排的「翻車實驗」,收尾時再預告第三次:

  1. 翻車①(M3 / M5,兩輪):同一句 prompt、同一個模型,全班的輸出各不相同;加上 AGENTS.md(always-on instructions)之後只收斂一半 → 這說明了為什麼需要 Skill,也劃出 instructions 與 Skill 的邊界。
  2. 翻車②(M8):環境裡有三個 Skill 之後,刻意用模糊指令觀察它選錯 → 這說明了為什麼 description 要寫對比句、什麼時候該把 Skill 鎖成只能手動叫。
  3. 翻車③(收尾預告,下半場 M9 解):三個 Skill 都在,一句複合指令下去,誰先跑、跑不跑、會不會越權動檔案,每次都不一樣 → 這是第五種資產 Custom Agent 存在的理由。

「照著步驟做完」的記憶兩週就淡了;「親眼看到它出事」的記憶會跟著你回到自己的專案裡。

M1 · 五種資產分工:Always-on Instructions / Prompt File / Skill / Custom Agent / MCP

這五個是你實際會「建立、存成檔案或設定」的資產。其中四個是可觸發、可叫用的能力,Always-on instructions(AGENTS.md,或 GitHub 專屬的 copilot-instructions.md)則是「一直都在」的底層規則,五者共同構成整組客製化的地基。上半場會親手做其中四種;第五種 Custom Agent 留到下半場 M9——它的價值是「組裝」,得先有東西可以組。先用一句話分清楚:

它是什麼 用一句話說
Prompt File 存成檔案、可重複叫用的指令範本 你把常用的「幫這個 PR 產生 release notes」指令存成 .prompt.md,之後每次直接 /release-notes 叫出來,不用重打
Custom Agent 一個聚焦、限縮工具的「人設」 用 @ 明確叫出來的角色,只給它特定工具跟特定指令,讓它專心做一件事(例如只做安全審查、不能改檔案)
Skill 固定情境 + 標準流程 + 判斷邏輯 針對一個明確的情境(例如「拿到會議逐字稿」),寫下標準流程、需要的輸入、判斷規則(什麼算決議、日期怎麼換算)與輸出格式;模型判斷情境相符時自動載入,不同人、不同專案執行結果一致
MCP 外部系統的標準化連接介面 「我跟 Outlook 日曆、Jira 溝通的插頭規格」——把外部系統的功能包成 Agent/Skill 可以呼叫的工具,本身不帶團隊的判斷邏輯
Always-on instructions
(AGENTS.md / copilot-instructions.md)		 一直都在、自動注入的專案層級規則 不用叫、每次請求都自動套用的「repo 預設規矩」——命名規範、安全預設、語言/風格慣例都寫這裡,是其他四種資產共用的底層基準

二個最像的:x vs y 逐對拆解

二種可叫用的資產之所以最難分,是因為它們兩兩之間都有一段模糊地帶。以下由「最像」排到「比較好分」,一次看懂邊界。分辨時只要問兩件事:是我喊、還是它自己判斷? 以及 它在管動作、身分、做法、還是連線?

①Prompt File vs. Skill 〈最像〉

兩者都是「可重複使用的工作流」,這是最像的地方。差別在誰觸發與帶不帶附件:

Prompt File Skill
觸發 你手動 打 /指令 模型自動發現、按需載入
載入方式 整份一次注入 漸進式:先讀 name+description,相關時才讀全文,附件再按需取用
帶附件 ✗ 就是一段文字(可帶 ${input:xxx} 變數) ✓ 資料夾可含 scripts / templates / 參考檔
檔案 .github/prompts/*.prompt.md .github/skills/<name>/SKILL.md

一句話:要一個「你自己喊、單檔、輕量」的招式 → Prompt File;要一個「模型自己判斷該用、還帶腳本範本」的完整 runbook → Skill。

②Skill vs. MCP

兩個常被當成同一類,其實本質相反——一個是「怎麼做」,一個是「連到哪」:

Skill MCP
負責 這件事該怎麼做的團隊 SOP(判斷層) 怎麼連上外部系統的工具(協定層)
本質 知識/程序 + 本地腳本 運行中的伺服器,提供活的工具/資料
帶團隊判斷? Skill 是 SOP,照著這份共識做,結果才會一致 MCP 是插頭規格——誰都能插,插了之後要幹嘛它不管

一句話 + Lab 7B 的 weekly-followup-planner 就是搭配使用:MCP 負責讀到你本週行事曆的忙碌與空檔;Skill 負責讀到之後——挑出可用空檔、把未結的 Action Item 排進去、決定輸出格式。

以下情境,各屬於 Prompt File / Custom Agent / Skill / MCP / Always-on instructions / Agent Mode 中的哪一個?

  1. 每週要摘要 10 場會議,輸出格式要一致,不管誰觸發結果都一樣。
  2. 只是這次臨時想把這段文字翻譯成英文,之後應該不會再用到。
  3. 需要讀取 Outlook 日曆上的會議資訊,這是跟外部系統對接的介面。
  4. 你想要一個「security reviewer」角色,只能讀程式碼、跑 linter,不能改檔案,之後用 @ 明確叫出來。
  5. 你在 chat 裡切成 Agent,讓 Copilot 自己規劃步驟、改檔案、跑測試直到完成——這個「自己規劃執行」的能力本身是什麼?
  6. 你常常要產生 PR 的 release notes,格式固定,於是存成範本,之後直接用 /release-notes 叫出來。

M2 · Context Engineering:先看兩個症狀,再對症下藥(講師 demo)

M0 的核心命題有三階。第一階「Prompt Engineering」大部份企業都已經做了;第三階「Skill Engineering」是今天的主軸。中間這一階——Context Engineering:控制模型每一次請求「看到什麼」——是多數人跳過的。這一節只有 10 分鐘的講師 demo:看兩個症狀、記住兩個動作(#file、新開 session)。完整的七層組裝表與 # 引用速查整理在附錄 A,回公司再翻。

症狀一:Agent 必須自行定位檔案

  1. 講師在 Portal 專案裡開著一個跟日期無關的檔案（例如 App.jsx），並在 Agent 模式詢問：「這個專案哪裡在做日期換算？」
  2. 打開 Developer: Show Chat Debug view，檢查第一個 panel/editAgent。測試結果顯示，開啟中的檔案會以 editorContext 提供檔案路徑，但不會自動附上完整原始碼。因此，「開啟檔案」不等於「把檔案內容加入 prompt」。
  3. 繼續查看後續的 runSubagent、grep_search 與 read_file。這些紀錄才顯示 Agent 實際搜尋了什麼、讀取了哪些檔案，以及工具結果如何進入下一次模型請求。回應底下的 references 可以協助確認引用來源，但不能取代完整的工具呼叫紀錄。
  4. 再使用 #file:App.jsx 明確附加檔案並重送相同問題。這次可在 attachments 中看到完整的 App.jsx 內容，證明明確附加與單純開啟檔案是兩種不同的 context 行為。

這次測試中，初始請求包含工作區資訊與目前檔案路徑，但沒有指出日期換算所在的檔案或 symbol。Agent 必須在迴圈中自行選擇搜尋方式、分析搜尋結果並讀取候選檔案。這不只是隨機猜測，而是由初始 context、搜尋查詢、工具結果與每一步的決策共同決定。若已知關鍵檔案，應明確附加；若不知道位置，則應要求 Agent 搜尋整個 codebase，並以函式定義及呼叫路徑驗證結論。

症狀二:不精準的 context 增加探索成本

  1. 新開一個 session，固定模型，送出不含附件的基準問題。點擊或 hover chat 輸入框的 Context Window 使用量指示器，記錄 Context Window、Session Cost、Files 與 Tool Results。
  2. 另開一個全新 session，把 src/ 資料夾拖進 chat，送出相同問題。資料夾附件只會提供路徑與目錄結構，不會把所有檔案全文加入 prompt；Agent 仍須自行搜尋及讀取檔案。本例的日期換算不在 src/，因此這是一個不精準的探索範圍。
  3. 再開一個全新 session，使用 #file 只附加真正包含日期換算的檔案，送出相同問題。這次完整檔案內容會直接進入 request，Agent 可以少做搜尋與讀檔。
  4. 比較三次的 Context Window、Session Cost、Files 與 Tool Results。若要確認差異來源，再打開 Agent Debug Logs → Summary，比較 input tokens、tool calls、cache reuse 與 credits。

本次測試中，附加正確檔案雖然提高了 Files 的占比，卻減少了 Agent 搜尋、讀檔與工具結果所需的 context，因此整體 token 與 credits 反而較低。重點不是「附件越少越省」，而是越早提供正確且最小的 authoritative context，Agent 越不需要花 token 探索錯誤範圍。實際差距仍會受到模型、回答長度、快取與工具決策影響，教學時應將數字視為這次實驗結果，而不是固定比例。

🔑兩個症狀,同一個核心問題

模型只能根據當次請求中的 instructions、訊息、context 與工具結果推理。找錯檔案或多繞路通常表示缺少足夠且精準的任務 context;探索成本偏高則可能來自不相關的歷史、附件、工具定義或工具結果。兩者都與 context 組裝有關,但 AI credits 還會受到模型、回答長度、推理量、工具呼叫與快取命中率影響,不能只歸因於附件大小。

為什麼會這樣:一次請求是七類來源組出來的

依 VS Code 官方文件,每次 agent 向模型發出請求時,VS Code 會從七類來源組裝 context:① system instructions、② 你的 customizations(AGENTS.md / instructions / skills / agents)、③ 這一句 user message、④ 對話歷史、⑤ 隱性 context(開著的檔案、選取範圍、Git 狀態)、⑥ 顯性引用(#、Add Context、拖放)、⑦ 工具輸出。症狀一出在第 ⑤ 層——開著檔案只帶進路徑,不帶內容;症狀二出在第 ④、⑦ 層——歷史與工具輸出堆積。七層各由誰決定、跟今天哪個模組有關,見附錄 A 的完整表格。

⚠️兩個常見的誤解,先更正
  • 「點開檔案,它就是這次請求的完整參考資料」——不成立。這輪實測顯示,Agent 模式會把 active file 的路徑放入 editorContext,但不會自動附上完整內容。使用 #file 明確附加後,完整檔案內容才出現在 request 的 attachments。若某個來源對任務很重要,應明確加入,不要只依賴目前開啟的 editor。
  • 「不加 #codebase,預設就會把整個 codebase 放進 prompt」——不成立。VS Code 的 workspace index 能協助 agent 搜尋相關程式碼,但不會把整個 workspace 塞進每一次請求。沒有顯性引用時,agent 會依問題、可用工具與搜尋結果決定是否搜尋、搜尋多深以及讀取哪些檔案。

對症下藥:記住兩個動作

  1. 已知關鍵檔案,就 #file 明確附加——不是點開就好。不知道在哪,給一個合理的範圍(拖資料夾縮小搜尋範圍),或直接讓 agent 搜——agent mode 內建 codebase search,#codebase 在 agent mode 多數是多餘的。引用的原則不是「多加幾個比較保險」,而是加入完成任務所需、最小且可信的來源。
  2. 換任務就新開 session——上一輪的訊息與工具結果會一直佔著 context,也會干擾新任務。長 session 可用 /compact 把舊對話壓成摘要騰出 context window,但不會退回已消耗的 credits。

等一下 M3、M5、M6 三輪實驗,每一輪都要新開 session,原因就在第二個動作:不新開,模型會參考自己上一輪的輸出。#terminalLastCommand、#web 等其他引用什麼時候才「不可取代」,見附錄 A 的速查表。

四區塊解剖

一個 SKILL.md = YAML frontmatter + Markdown 內文。四個區塊職責不同,而且分成兩種完全不同的「被讀取時機」——這個時機差異,是能不能寫對的關鍵:

區塊 作用 寫不好會怎樣(對照你剛剛在 M3 / M5 看到的)
frontmatter description 選前讀:決定「要不要選中這個 Skill」。要同時寫清楚「做什麼 + 何時用 + 不是什麼」的對比句 + 關鍵詞 太泛 → 亂觸發或不觸發;跟其他 Skill 描述太像 → 選錯(M8 會實測這件事)
① 適用範圍 / 不適用時改用 選後讀:被選中之後再次確認「這次任務真的歸我管嗎」,不歸我管該轉去哪 誤以為這裡也在做觸發判斷,同一件事寫兩次、兩次還不一致
② 需要的輸入 來源、格式、必填項;缺了要反問 M3 裡「沒抓到會議日期就無法換算 Due Date」——自己亂假設,輸出歪掉
③ 步驟 一步步怎麼做 M3 裡的結構偏離預期——純靠 LLM 自由發揮,每次不一樣
④ 輸出格式 格式、結構要可驗收 M3 裡有人表格有人流水帳——每次長得不一樣,沒人敢直接拿來用
⚠️為什麼需要「① 適用範圍 / 不適用時改用」

它的角色是 recovery(選錯之後給 Copilot 一條回頭路),不是 prevention(選前防呆,那是 description 的工作)。

⚠️③ 步驟只寫文字敘述,收斂力有限

設計方法:Scope / IO

Scope 怎麼抓——優先權判斷,不是只看一句話長短

  1. 工具/寫入權限邊界是否不同(有沒有副作用、要不要額外認證)→ 不同就該拆,不管兩件事是不是永遠一起發生。
  2. 是否永遠嚴格共同觸發、有強依賴順序 → 傾向合併成一個 Skill 裡的多步驟。
  3. 未來會不會被其他情境單獨呼叫 → 前兩者都中性時的 tie-breaker。

用 meeting-summary 實際套一次:

  • 權限邊界:「產生摘要」跟「抽取待辦」都是唯讀逐字稿、不寫外部系統——邊界一樣,不構成拆開理由。
  • 共同觸發:拿到逐字稿,PM 通常同時要摘要(報告用)也要待辦清單(追蹤用)——成立,指向合併。
  • 單獨呼叫:目前看不出來——中性。

所以 meeting-summary 一次輸出四個區塊:摘要、決議、風險、待辦。「一句話講得完」可以當直覺起手式,但不是唯一判準——如果兩件事永遠綁在一起(例如摘要完順便建 Jira 票),句子只是變長,測試照樣通過,卻掩蓋了權限邊界不同的事實。這也是為什麼下半場 M11 的 Jira 整合是獨立 Skill:建票要寫入外部系統、要額外認證,第一條判準就把它擋在外面。

IO 怎麼定

  • 輸入:講清楚來源、格式、必填項;缺了要反問,不要自己假設。這個 Skill 因為要換算待辦到期日,會議日期是必要輸入——「這週五」「下週三」這種相對日期,沒有基準日無法換算(M3 你已經看過沒有這條規則時會發生什麼事)。
  • 輸出:要可驗收——指定哪些區塊、什麼格式。模糊的輸出等於每次都不一樣,團隊沒辦法把它當「資產」用。

# 會議逐字稿整理 Skill(Meeting Notes Skill)

## ① 適用範圍 / 不適用時改用
- 適用:使用者提供一份會議逐字稿或會議紀錄全文,並要求產生摘要、決議、風險、或待辦事項——四項只要要求其中任何一項,都由這個 Skill 一次處理。
- 不適用:使用者只是「討論某個主題」、沒有提供實際逐字稿內容——直接對話回答就好。
- 不適用:使用者要的是看本週空檔、把未結事項排進去跟進 → 改用 weekly-followup-planner。

## ② 需要的輸入
1. 會議逐字稿全文(必要)。
2. 會議日期(必要)。逐字稿裡的期限常是「這週五」「下週三」這種相對日期,沒有基準日無法換算,缺少時要先反問使用者。
3. (選)與會人員名單。沒有名單對照時,保留逐字稿原始代稱,不要自己編造人名。

## ③ 步驟
1. 通讀全文,辨識主要議題。
2. 萃取「目前狀態」,合併成 3-4 句話的專案進度摘要。
3. 找出所有「明確被拍板同意」的事項列為 Decisions——只有真正拍板的才算,單純討論或提議不算。
4. 找出所有被明確提及、可能影響進度或合規的疑慮,列為 Risks——每一項要對應具體發言,不能是自己推論。
5. 找出所有「A 對 B 明確指派任務」或「某人主動承諾要做某件事」的語句。
6. 對每一筆任務萃取 Owner(實際姓名,不用職稱)、Action(具體動詞+受詞)、Due Date(依②的會議日期換算成 YYYY-MM-DD,完全沒提到期限則標記「未訂」)、Priority(沒有語氣線索一律 Medium)。
7. 同一人多筆任務分開列出,不要合併成一筆。
8. 依 ④ 的格式整理輸出。

## ④ 輸出格式
```markdown
## Meeting Summary
<一段 3-4 句話的專案進度摘要>

## Decisions
1. <決議事項一>
...

## Risks
- <風險項目一>
...

## Action Items
| Owner | Action | Due Date | Priority |
|---|---|---|---|
| <姓名> | <具體任務> | <YYYY-MM-DD 或「未訂」> | <High/Medium/Low> |
```
四個區塊都要有,即使某區塊為空也要明確寫「無」,不要省略整個區塊。

GitHub Copilot 的 Skill selection 是機率性語意匹配——description 不夠具體、沒有清楚的對比詞,多個 Skill 之間就會互相干擾、選錯或選不到。理論講完了,接下來 15 分鐘直接測。

  5. 修復回合:挑一句你這邊選錯(或不觸發)的指令,回頭改對應 Skill 的 description——加對比句、加關鍵詞、或把容易誤導的詞拿掉——再測一次,確認行為改變。

A.2 · # 引用速查:哪些是最佳化、哪些不可取代

顯性引用(第 6 層)是你控制任務來源 context 最直接的方式。你同時也能控制 user message、session 邊界、customizations、可用工具與模型選擇。引用的原則不是「多加幾個比較保險」,而是加入完成任務所需、最小且可信的來源。

但必要性要分層看。Agent mode 本身就會自主搜尋、讀檔、抓網頁,所以多數引用在 agent mode 下是最佳化(省 turn、消歧義、讓輸入可重現),而不是必要條件。真正不可取代的只有一類:agent 根本沒有對等工具可以取得的來源。

B.1 · Auto 的運作方式與三個實務注意事項

依官方文件,Auto(task optimization)結合兩個系統:一個追蹤即時系統健康與可用性,一個評估任務複雜度,逐 prompt把任務路由到最適合的模型——把高成本的推理模型保留給真正需要的問題,直接的任務交給較快、較低成本的模型。可選的模型是你的方案與管理員政策允許的模型,不在方案內或被政策排除的模型不會被選用。

注意事項官方說法實務影響建議
① Tier 決定路由偏好提供三個 tier:Efficiency(成本優先)、Balance(成本、品質、延遲平衡)、Intelligence(品質優先)。三個 tier 共用同一組可選模型。評估是逐 prompt 做的,但切換受 cache 邊界約束(見②),實務上第一輪選定後同一 session 多半沿用同一個模型。既然模型大致是開場那一刻決定的,開場的 tier 就是整個 session 的品質上限。用 Efficiency 開一個長 agentic session,等於一路用便宜模型跑完;而且不會有任何提示——你只看到結果變差,不知道原因是模型不是 prompt。開 session 前先確認 tier,而不是跑到一半才想起來。長 agentic 任務改 Intelligence;需要可重現或跨環境一致,直接鎖具名模型(代價是失去 Auto 的 10% 折扣)
② 切換模型與 cache「路由沿自然的 cache 邊界進行,以避免額外的 cache 相關成本。session 中途切換模型會增加成本,且品質未見相應提升。」這就是①「評估逐 prompt、但模型不常變」的原因:換模型會踩破 prompt cache,新模型沒有既有 cache,整段上下文要重送重算,所以 Auto 每輪評估的結果幾乎都是維持現狀。同樣的代價落在你手動切換上——在第 12 輪換模型,上下文重新送、重新計費,且新模型對前面指令的理解可能不同一個 session 一個模型;要換就新開 session,並用 # 把必要 context 重新給齊。長任務寧可一開始就選對,不要中途修正
③ 可重現性Auto 依任務複雜度與系統狀態選模型;模型名單會隨時間改變同一句 prompt 在不同時間可能由不同模型回答——這就是今天 M3 / M5 / M6 三輪全班鎖同一模型的原因:先把這個變因拿掉需要 before/after 比對、回歸測試、或團隊共用資產時,鎖模型並記錄模型名稱
