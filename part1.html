📌講義設計原則

「先定終點,再把技術主題掛在功能上」——每個重要觀念,都先讓你親眼看到沒有它會出什麼事,再教你解法。 全天有三次刻意安排的「踩坑」:

  1. M2a ·翻車實驗:同一句 prompt,全班跑出來的結果長得都不一樣 → 這就是為什麼需要 Skill。
  2. M3c · 誤觸發實測:環境裡有三個 Skill 之後,刻意用模糊指令看它選錯 → 這就是為什麼 description 要寫對比句。
  3. M3d · 編排失控:三個 Skill 都在,但一句複合指令下去,誰先跑、跑不跑、會不會越權動你的檔案,每次都不一樣 → 這就是為什麼要用 Custom Agent 把能力與工具權限收斂成一個角色。
  4. M4 · 純手刻漂移:同一份規格純手刻兩次,資料結構長得不一樣 → 這就是為什麼 scaffolding Skill 要包決定性工具。

「照著步驟做完」的記憶兩週就淡了;「親眼看到它出事」的記憶會跟著你回到自己的專案裡。

M1 · 四種資產分工:Prompt File / Custom Agent / Skill / MCP(＋ copilot-instructions 底層規則)

這四個是你實際會「建立、存成檔案」的資產,最容易混淆;再加上 copilot-instructions 這一層「一直都在」的規則,構成整組客製化的地基。先用一句話分清楚:

它是什麼 用一句話說
Prompt File 存成檔案、可重複叫用的指令範本 你把常用的「幫這個 PR 產生 release notes」指令存成 .prompt.md,之後每次直接 /release-notes 叫出來,不用重打
Custom Agent 一個聚焦、限縮工具的「人設」 用 @ 明確叫出來的角色,只給它特定工具跟特定指令,讓它專心做一件事(例如只做安全審查、不能改檔案)
Skill 把成熟做法包成能力模組 「某類任務的標準做法」,可重複用,不容易走鐘,不同人、不同專案做出來的結果都差不多
MCP 外部系統的標準化連接介面 「我跟 Outlook 日曆、Jira 溝通的插頭規格」——把外部系統的功能包成 Agent/Skill 可以呼叫的工具,本身不帶團隊的判斷邏輯
copilot-instructions 一直都在、自動注入的專案層級規則 不用叫、每次請求都自動套用的「repo 預設規矩」——命名規範、安全預設、語言/風格慣例都寫這裡,是上面四種資產共用的底層基準

四個最像的:x vs y 逐對拆解

這四種資產之所以最難分,是因為它們兩兩之間都有一段模糊地帶。以下由「最像」排到「比較好分」,一次看懂邊界。分辨時只要問兩件事:是我喊、還是它自己判斷? 以及 它在管動作、身分、做法、還是連線?

①Prompt File vs. Skill 〈最像〉

兩者都是「可重複使用的工作流」,這是最像的地方。差別在誰觸發與帶不帶附件:

Prompt File Skill
觸發 你手動 打 /指令 模型自動發現、按需載入
載入方式 整份一次注入 漸進式:先讀 name+description,相關時才讀全文,附件再按需取用
帶附件 ✗ 就是一段文字(可帶 ${input:xxx} 變數) ✓ 資料夾可含 scripts / templates / 參考檔
檔案 .github/prompts/*.prompt.md .github/skills/<name>/SKILL.md

一句話:要一個「你自己喊、單檔、輕量」的招式 → Prompt File;要一個「模型自己判斷該用、還帶腳本範本」的完整 runbook → Skill。

②Prompt File vs. Custom Agent

兩者都在 .github/ 下、都能綁 tools/model——差別在生命週期:

Prompt File Custom Agent
本質 動詞(做這件事) 身分(你現在是誰)
生命週期 跑一次就結束 切進去後,整段對話都是它
管什麼 這次的任務內容 人設 + 能碰哪些工具(可設唯讀)
agent: 的位置 頂層欄位:我(這個 prompt)要用哪個 agent 的身分執行 巢狀在 handoffs裡:對話結束後可以交接給哪個 agent

一句話:Prompt 是「做這件事」,Agent 是「你現在以什麼身分、能碰什麼」。

③Skill vs. Custom Agent

兩個都是「事先寫好、之後重複用」,差別在定義的層面:

Custom Agent Skill
定義層面 誰 + 能碰什麼(人設、限定工具集、模型) 怎麼做(步驟、判斷邏輯、輸出格式)
觸發 你主動切換成這個角色 模型判斷相關時自動翻開
關係 上游:一個被限定角色的員工(Custom Agent) 下游:做事時依然要照公司的 SOP(Skill)走

一句話:Agent 決定「以什麼身分、可以做什麼」;Skill 提供「這件事該怎麼做」的手冊。

④Skill vs. MCP

兩個常被當成同一類,其實本質相反——一個是「怎麼做」,一個是「連到哪」:

Skill MCP
負責 這件事該怎麼做的團隊 SOP(判斷層) 怎麼連上外部系統的工具(協定層)
本質 知識/程序 + 本地腳本 運行中的伺服器,提供活的工具/資料
帶團隊判斷? Skill 是 SOP,照著這份共識做,結果才會一致 MCP 是插頭規格——誰都能插,插了之後要幹嘛它不管

一句話 + Lab 3B 的 weekly-followup-planner 就是搭配使用:MCP 負責讀到你本週行事曆的忙碌與空檔;Skill 負責讀到之後——挑出可用空檔、把未結的 Action Item 排進去、決定輸出格式。

進 Lab 前,先自我檢測一下

以下情境,各屬於 Prompt File / Custom Agent / Skill / MCP / copilot-instructions / Agent Mode 中的哪一個?

  1. 每週要摘要 10 場會議,輸出格式要一致,不管誰觸發結果都一樣。
  2. 只是這次臨時想把這段文字翻譯成英文,之後應該不會再用到。
  3. 需要讀取 Outlook 日曆上的會議資訊,這是跟外部系統對接的介面。

  5. 你在 chat 裡切成 Agent,讓 Copilot 自己規劃步驟、改檔案、跑測試直到完成——這個「自己規劃執行」的能力本身是什麼?
  6. 你常常要產生 PR 的 release notes,格式固定,於是存成範本,之後直接用 /release-notes 叫出來。
  7. 你希望這個 repo 每次請求都自動套用團隊命名規範與安全預設,不用任何人記得去啟用。
點我看答案

  2. 一次性提問,連 Prompt File 都不用建立
  3. MCP(協定層,對接外部系統)
  4. Custom Agent(限定工具、固定人設、明確叫用)
  5. Agent Mode(執行引擎本身,不是你建立的資產)
  6. Prompt File(存起來的範本,重複叫用)
  7. copilot-instructions(一直都在的規則,每次自動套用)

M2a · 翻車①:漂移實驗——同一句 prompt,N 種輸出

在學任何 SKILL.md 語法之前,先做這個 15 分鐘的實驗。

📄lab2-meeting-summary-skill/sample-transcript.txt— 全班共用的同一份逐字稿

操作(每個人都做,不要跳過):

  1. 開一個乾淨的環境——確認 .github/skills/ 底下沒有任何 Skill、沒有特別的 instructions。
  2. 把 sample-transcript.txt 內容貼進 Copilot Chat,只下這一句:「幫我整理這場會議的紀錄」。一字不多、一字不少,全班用同一句。
  3. 跑完後不要修、不要重跑,保留第一次的輸出。
  4. 講師現場抽 3-4 位學員,把輸出投影並排比對。

比對時盯著這四個點看:

檢查點 你會看到的漂移
輸出結構 有人被分成摘要/決議/待辦,有人是一大段流水帳,有人多了「討論重點」這種自創區塊
Due Date 逐字稿裡 David 說「這週五前」、George 說「下週三前」——有人換算成實際日期,有人照抄相對用詞,有人乾脆沒抓到期限
Decisions 判定 「跟 SAP 整合」在逐字稿裡明講「先不排進 PoC 範圍」——有人正確排除,有人把它列成決議或待辦
Owner 欄位 有人寫姓名(David / Mary / George),有人寫職稱(架構師 / 財務窗口)

然後回到 M0 留下的那個提問:「把 prompt 傳給同事」為什麼不夠?——你們剛剛全班用的是同一句 prompt、同一份輸入,輸出還是長得不一樣。這不是誰的 prompt 寫得不好,是 LLM 生成本質上的 sampling variance:沒有被固定下來的判斷(什麼算決議、日期怎麼換算、欄位長怎樣),每次都會重新被「發明」一次。

這就是 Consistency Gap 的長相。接下來 65 分鐘,我們把它收斂掉——收斂完之後,你會用同一句指令再跑一次,親眼對比前後差異。

M2b · SKILL.md 四區塊解剖 + Lab 2:meeting-summary

四區塊解剖

一個 SKILL.md = YAML frontmatter + Markdown 內文。四個區塊職責不同,而且分成兩種完全不同的「被讀取時機」——這個時機差異,是能不能寫對的關鍵:

區塊 作用 寫不好會怎樣(對照你剛剛在 M2a 看到的)
frontmatter description 選前讀:決定「要不要選中這個 Skill」。要同時寫清楚「做什麼 + 何時用 + 不是什麼」的對比句 + 關鍵詞 太泛 → 亂觸發或不觸發;跟其他 Skill 描述太像 → 選錯(M3c 會實測這件事)
① 適用範圍 / 不適用時改用 選後讀:被選中之後再次確認「這次任務真的歸我管嗎」,不歸我管該轉去哪 誤以為這裡也在做觸發判斷,同一件事寫兩次、兩次還不一致
② 需要的輸入 來源、格式、必填項;缺了要反問 M2a 裡「沒抓到會議日期就無法換算 Due Date」——自己亂假設,輸出歪掉
③ 步驟 一步步怎麼做 M2a 裡的結構漂移——純靠 LLM 自由發揮,每次不一樣
④ 輸出格式 格式、結構要可驗收 M2a 裡有人表格有人流水帳——每次長得不一樣,沒人敢直接拿來用
⚠️為什麼需要「① 適用範圍 / 不適用時改用」

它的角色是 recovery(選錯之後給 Copilot 一條回頭路),不是 prevention(選前防呆,那是 description 的工作)。

⚠️③ 步驟只寫文字敘述,收斂力有限

設計方法:SKill邊界

Skill邊界 怎麼抓——優先權判斷,不是只看一句話長短

  1. 工具/寫入權限邊界是否不同(有沒有副作用、要不要額外認證)→ 不同就該拆,不管兩件事是不是永遠一起發生。
  2. 是否永遠嚴格共同觸發、有強依賴順序 → 傾向合併成一個 Skill 裡的多步驟。
  3. 未來會不會被其他情境單獨呼叫 → 前兩者都中性時的 tie-breaker。

用 meeting-summary 實際套一次:

  • 權限邊界:「產生摘要」跟「抽取待辦」都是唯讀逐字稿、不寫外部系統——邊界一樣,不構成拆開理由。
  • 共同觸發:拿到逐字稿,PM 通常同時要摘要(報告用)也要待辦清單(追蹤用)——成立,指向合併。
  • 單獨呼叫:目前看不出來——中性。

所以 meeting-summary 一次輸出四個區塊:摘要、決議、風險、待辦。「一句話講得完」可以當直覺起手式,但不是唯一判準——如果兩件事永遠綁在一起(例如摘要完順便建 Jira 票),句子只是變長,測試照樣通過,卻掩蓋了權限邊界不同的事實。這也是為什麼 M5 的 Jira 整合是獨立 Skill:建票要寫入外部系統、要額外認證,第一條判準就把它擋在外面。

IO 怎麼定

  • 輸入:講清楚來源、格式、必填項;缺了要反問,不要自己假設。這個 Skill 因為要換算待辦到期日,會議日期是必要輸入——「這週五」「下週三」這種相對日期,沒有基準日無法換算(M2a 你已經看過沒有這條規則時會發生什麼事)。
  • 輸出:要可驗收——指定哪些區塊、什麼格式。模糊的輸出等於每次都不一樣,團隊沒辦法把它當「資產」用。

# 會議逐字稿整理 Skill(Meeting Notes Skill)

## ① 適用範圍 / 不適用時改用
- 適用:使用者提供一份會議逐字稿或會議紀錄全文,並要求產生摘要、決議、風險、或待辦事項——四項只要要求其中任何一項,都由這個 Skill 一次處理。
- 不適用:使用者只是「討論某個主題」、沒有提供實際逐字稿內容——直接對話回答就好。
- 不適用:使用者要的是看本週空檔、把未結事項排進去跟進 → 改用 weekly-followup-planner。

## ② 需要的輸入
1. 會議逐字稿全文(必要)。
2. 會議日期(必要)。逐字稿裡的期限常是「這週五」「下週三」這種相對日期,沒有基準日無法換算,缺少時要先反問使用者。
3. (選)與會人員名單。沒有名單對照時,保留逐字稿原始代稱,不要自己編造人名。

## ③ 步驟
1. 通讀全文,辨識主要議題。
2. 萃取「目前狀態」,合併成 3-4 句話的專案進度摘要。
3. 找出所有「明確被拍板同意」的事項列為 Decisions——只有真正拍板的才算,單純討論或提議不算。
4. 找出所有被明確提及、可能影響進度或合規的疑慮,列為 Risks——每一項要對應具體發言,不能是自己推論。
5. 找出所有「A 對 B 明確指派任務」或「某人主動承諾要做某件事」的語句。
6. 對每一筆任務萃取 Owner(實際姓名,不用職稱)、Action(具體動詞+受詞)、Due Date(依②的會議日期換算成 YYYY-MM-DD,完全沒提到期限則標記「未訂」)、Priority(沒有語氣線索一律 Medium)。
7. 同一人多筆任務分開列出,不要合併成一筆。
8. 依 ④ 的格式整理輸出。

## ④ 輸出格式
```markdown
## Meeting Summary
<一段 3-4 句話的專案進度摘要>

## Decisions
1. <決議事項一>
...

## Risks
- <風險項目一>
...

## Action Items
| Owner | Action | Due Date | Priority |
|---|---|---|---|
| <姓名> | <具體任務> | <YYYY-MM-DD 或「未訂」> | <High/Medium/Low> |
```
四個區塊都要有,即使某區塊為空也要明確寫「無」,不要省略整個區塊。

  2. 模糊指令二:附上 sample-transcript.txt,說:「幫我把會議裡的待辦整理一下,排個計畫」。——「整理待辦」指向 meeting-summary,「排個計畫」同時沾到 wbs-generator(拆解)跟 weekly-followup-planner(排程)。
  3. 模糊指令三:「我下週要跟進這個專案,幫我準備一下」。——沒有任何一個 Skill 的關鍵詞被直接命中,看它會硬選一個、還是不觸發。
  4. 講師收集現場結果:同一句指令,不同人的機器選中的 Skill 很可能不一樣——這本身就是最重要的觀察:selection 是機率性的,description 的工作是把機率分佈收窄,不是給出保證。
  5. 修復回合:挑一句你這邊選錯(或不觸發)的指令,回頭改對應 Skill 的 description——加對比句、加關鍵詞、或把容易誤導的詞拿掉——再測一次,確認行為改變。

改完之後,養成兩個帶得走的習慣:

  • description 用對比句法,不是只堆關鍵詞:「是逐字稿產出的結構化紀錄,不是排程規劃」,而不是單純寫「摘要、逐字稿、summary」。
  • 新增 Skill 時,把新舊 description 一起丟給 Copilot,問「這兩個會不會混淆、什麼情況下會選錯」——不需要自動化互斥檢查,但至少人工過一次這道關。
📌這個實驗跟下半場的關係

企業內部很快會累積 5-10 個以上相似的 Skill,誤觸發從「偶發」變「日常」。M6 的品質治理會把今天這 15 分鐘的手動測試,升級成有版本紀錄、有回歸測試觀念的治理流程——你現在做的,就是那套流程的最小可行版。

M3d · 翻車③:Custom Agent——把三個 Skill 組裝成一個會議助手

提出解法前的誠實時刻:Custom Agent 鎖得住什麼、鎖不住什麼

🔑一護欄一行為準則:兩種完全不同強度的收斂

依照目前 GitHub Copilot 的 .agent.md 規格,Custom Agent 給你的是兩種強度不同的收斂手段,千萬不要混為一談:

重點來了:tools 欄位只收工具名(內建工具、tool sets、MCP 工具)——frontmatter 裡沒有任何「Skill 白名單」欄位。Skill 的觸發永遠走 description 語意匹配(M3c 練的那一層),Custom Agent 改變的是「以什麼人設、帶著哪些工具」去做匹配,而不是把其他 Skill 從選單上拿掉。

那 Skill 層有沒有「護欄」?有——但它長在 SKILL.md 自己身上,就是 M2b 認識過的 disable-model-invocation: true(該 Skill 從此只能手動 /skill-name 叫用,不會被任何 agent 自動選中)。所以完整的治理拼圖是:工具的護欄蓋在 agent 上,Skill 的護欄蓋在 Skill 上,行為準則寫在 agent 的 body 裡。記住這張拼圖——下半場你會遇到一個 tools 白名單管不到、只能靠 Skill 自己這道護欄的場景。

🔑這一解法跟 M3c 的差別

M3c 的 description 對比句,收的是「哪個 Skill 被選中」的機率。Custom Agent 的路由規則,收的是「這個角色會怎麼編排」的機率——固定人設 + 明確路由,讓同一句複合指令每次走同一條路。而 tools 白名單處理的是另一個維度:就算路由漂了,它能造成的傷害被護欄限制住。三個槓桿疊加使用——description(M3c)、路由指令(現在)、工具邊界(現在)——不是三選一。

提出解法:一個「編排型」Custom Agent

# 會議營運助手(Meeting Ops Agent)

你是會議逐字稿的下游營運助手。你**不自己發明「怎麼做」**——所有實際產出都交給對應的
Skill,你只負責路由、補齊必要輸入、守住邊界。

## 路由規則(薄路由,不重寫 SOP)
你只使用以下三個 Skill,除此之外的 Skill 一律不採用:
- 給逐字稿、要摘要/決議/風險/待辦 → 使用 meeting-summary
- 要把範圍拆成 WBS / Excel          → 使用 wbs-generator
- 問「本週哪些時段有空、把未結事項排進去」→ 使用 weekly-followup-planner
- 一句話同時要「整理+排計畫」時,先做 meeting-summary,再把產出的 Action Items
  交給 weekly-followup-planner,並向使用者說明你的順序。
- 缺會議日期時先反問(延續 meeting-summary ② 的必要輸入),不要自己假設。

## 邊界(能碰什麼/不能碰什麼)
- 只在會議產出範圍內工作;不修改 Portal 應用程式原始碼。
- 需要寫入外部系統(例如建 Jira 票)時,明講超出範圍、交還使用者,不要自己找工具硬做。

@meeting-ops 從骨架到能用，中間有五個容易踩空的細節——存哪裡、叫誰、description 寫給誰看、tools 怎麼填才不會蓋出「假護欄」。以下把後半段拆成五個決策點,並用兩個符號貫穿全程。

02 / 05 — description 這行字,到底寫給誰看?

meeting-ops 是 @ 手動叫出來的,這種情況下 description 的閱聽眾是人——它只出現在下拉選單、輸入框的 placeholder 文字裡,幫你或同事判斷「這是不是我要的角色」,寫成人話就好,不用刻意塞觸發關鍵詞。

🧱但如果哪天它被掛進更大的編排,閱聽眾會換人

Custom Agent 可以被另一個 agent 當成 subagent 呼叫。這種情境下,決定「該不該選中它」的不再是人眼掃過下拉選單,而是模型讀 description 來判斷——跟 SKILL.md 的 description 是同一種機制:要包含「做什麼、何時該選我」。今天的骨架只走純手動叫用這條路,所以現在不用改寫法;但理解這個切換點,是看懂下一節「subagent 授權」在防什麼的前提。

03 / 05 — 你的 agent 會不會被拉去當 subagent?

一個常見誤解:「我的 .agent.md 裡沒寫 agents 欄位,所以沒有人可以呼叫到我」——方向反了。agents 欄位是寫在呼叫者身上的允許清單(主動把子任務發派給其他 agent 處理),不是寫在被呼叫者身上的門禁。

⚠️預設值是開放的

只要你沒有主動設 disable-model-invocation: true,你的 agent 就預設可以被任何有 agent tool、且把它列進自己 agents 陣列(或用 *)的 coordinator agent 當成 subagent 呼叫。「沒寫 agents 欄位」跟「不會被呼叫」完全是兩件事。

你想要的結果 該怎麼設 設在誰身上
預設行為:可以被任何 coordinator 呼叫 什麼都不用寫 —
完全不能被當 subagent,只能 @ 手動叫 disable-model-invocation: true 寫在自己的 .agent.md
平常鎖死,但某個信任的 coordinator 仍可呼叫 自己設 disable-model-invocation: true,coordinator 的 agents 陣列明確列出你的名字 兩邊都要設

最後一列的關鍵細節:被明確列進 agents 陣列,會覆蓋它自己的 disable-model-invocation: true——這是「預設鎖死、對信任對象開白名單放行」的設計,跟今天 tools 白名單的邏輯是同一種精神,只是防的方向不同:tools 防「meeting-ops 能碰什麼工具」,這裡防「meeting-ops 會不會被其他 agent 拉去用」。

04 / 05 — tools 白名單:不要背拼法,用工具選單勾

tools 的合法值是內建工具、tool sets、MCP 工具(整個 MCP server 用 <server 名>/*)。填了不存在的名稱不會報錯,只會被靜默忽略——這是最危險的失效模式:你以為蓋了護欄,其實沒有。

正確做法不是背拼法,而是在 Agent Customizations editor(Chat 齒輪 → Agents)裡編輯 agent 時,用工具勾選清單產生名稱;骨架裡的 'edit'、'runCommands' 以你環境實際顯示的為準。

⚠️tools 裡的 MCP 工具名 = mcp.json 的 server key,不是工具本身的名字

最容易對不到的就是 MCP 工具。tools 認的是你 mcp.json 裡 servers 底下那個 key,命名慣例是 <server-name>/<tool-name>(整個 server 全放行就用 <server-name>/*)。

jsonc
// .vscode/mcp.json
"servers": {
  "agent365-calendartools": { /* ... */ },   // ← server-name 就是這個 key
  "microsoft-learn":         { /* ... */ },
  "github":                  { /* ... */ }
}

要放行整個行事曆 server,寫的是 agent365-calendartools/*。若只寫 agent365-calendartools(少了 /),就不符合 server/tool 慣例——就算它剛好跟某個工具同名,也對不到任何「內建工具、別名、或 server/tool pattern」,一樣被靜默忽略。這正是「假護欄」:名字沒填對,護欄根本沒蓋起來,而且不會報錯。實務上別手打,用 VS Code 的工具勾選清單產生名稱。

  1. 建立 .github/agents/meeting-ops.agent.md,對照骨架自己寫一版——特別是 description(這是 agent 被 @ 叫用時的自我說明)與路由規則。tools 用工具選單勾選確認名稱。
  2. 用 @meeting-ops 重跑剛剛翻車那一句:「這是這場會議的逐字稿,幫我把該做的都做一做。」 這是今天第二次 before/after(第一次是 M2a→Lab 2)。
  3. 對比兩點:行為是不是收斂了(每次路由到同一組 Skill、順序一致)、以及它有沒有守在會議範圍內、沒去動不相關的檔案。
  4. 刻意測一次邊界:叫它「順便幫我把這些 Action Item 開成 Jira 票」——確認它拒絕並交還,而不是硬找工具做。順帶想一下:它現在拒絕,靠的是行為準則(body 指令)還是護欄(tools 白名單)?——兩者都有:Jira 工具不在白名單裡(護欄),邊界規則也叫它交還(行為準則)。但這道 tools 護欄只攔得住「透過獨立工具」的寫入——如果哪天有個 Skill 是靠你已經放行的工具(例如終端機)去打外部系統,這道護欄還擋得住嗎?先想著,下半場會給你一個答案。

三個最容易踩的雷

  • 別把 SOP 抄進 agent:一旦把「怎麼做」複製進 .agent.md,就跟 Skill 重複、日後兩邊不同步——正是 M1 警告過的反例。Agent 裡只放路由,不放步驟。
  • 別以為沒寫 agents 欄位就沒人能呼叫你:agents 欄位是呼叫者的允許清單,不是你的門禁。真的要防被拉去當 subagent,得自己設 disable-model-invocation: true。
  • Custom Agent 不是 selection 正確性的保證:路由規則是強力行為準則,但 description 對比句(M3c 練的)還是要寫好——行為準則與機率收斂疊加,才有穩定行為。

M4 · OpenAPI → FastAPI Scaffolding + 翻車④:純手刻漂移

這是今天技術密度最高的一段,對應企業導入 Copilot 最常見的具體需求:「從 API Spec 產生 Controller 骨架」。而這份規格就是 Portal 自己的後端 API——做完這一步,M0 demo 裡的前端終於有真正的後端可以接,故事線閉環。

🔑本堂最重要的一個觀念(不踩雷的關鍵)

最穩的 scaffolding Skill,通常不是叫 LLM 純手寫,而是讓步驟去「包一個既有的決定性工具」、再疊上團隊規範與品質自檢。這裡用 datamodel-codegen 從 OpenAPI 規格產生 Pydantic model,Skill 負責「呼叫工具 + 套 router 慣例 + 自檢」。

Lab 4 第一輪就是讓你親手做對照組:同一份規格純手刻兩次,再用包工具的 Skill 跑兩次,把四份輸出攤開來 diff。你在 M2a 已經看過漂移這個模式,只是這次漂移換了一個層次:輕則類別命名、enum member 大小寫不一致(換一次產出,呼叫端的 Sentiment.positive 可能直接 AttributeError),重則型別本身對不上——不是格式難看那種一眼看得出來的漂移,是「兩份看起來都對,但兜不起來」的漂移。

適用前提:這個做法假設 OpenAPI spec 已經定案(治理委員會審過、或對外合約規格)。

📌跟「Spec-Driven Development(SDD)」是同一件事嗎?

不是同一個量級。今天只處理「規格 → 介面骨架」這一段轉譯,規格已定案、不涉及協商。GitHub Spec Kit、Amazon Kiro 這類 SDD 工具鏈管的是規格從模糊需求到定案的全流程(constitution → specify → plan → tasks → implement),範圍大得多。兩者不是替代關係——今天教的是規格定案後怎麼穩定落地。

設計題 我們的決定
Scope(一句話) 「給我 OpenAPI 規格,我給你 FastAPI 的 router 骨架 + Pydantic model」
輸入 OpenAPI yaml/json 檔路徑;輸出目錄
輸出 app/models/schemas.py + app/routers/<tag>.py + app/main.py
步驟核心 包工具:datamodel-codegen 產 model → 依 tag 分 router → 每個 operationId 一個函式骨架
品質規則 endpoint 無遺漏、response_model 對齊、骨架內不可夾帶幻覺商業邏輯、uvicorn 能啟動、重跑不覆蓋已有實作
📌品質規則最後一條為什麼存在(講給你聽,今天不撞)

「重跑不覆蓋已有實作」防的是另一種真實事故:spec 改版後重跑 scaffold,把同事上週手寫好的商業邏輯靜默蓋回骨架,而且 git diff 裡看起來就像一次普通的重新生成。今天篇幅只夠撞一次護欄,我們把實測留給漂移;但請記住這條規則的來歷——Skill 的品質規則,最有價值的那幾條,往往來自事故,不是來自想像。下半場 M6 的「品質規則硬化與版本升級」講的就是怎麼把這件事制度化。

Lab 4:純手刻 vs 包工具——同一份規格,四份輸出攤開比 (Lab ★)

這個 Lab 跟前兩個結構不同:不要求你從頭手寫 SKILL.md(今天已經寫過三份,第四份的邊際學習有限),而是把時間花在「先看純手刻怎麼翻車,再看包工具為什麼穩」。這裡的翻車跟覆蓋不同,它是機率性的——單看一份純手刻的輸出,常常「看起來還不錯」,所以我們的比法不是比對錯,而是比兩次跑得一不一樣:同一份規格、同一句指令,跑兩次長得不一樣,就代表你不能把它當可靠的工程步驟。

📄lab4-openapi-fastapi-scaffold/skills/openapi-to-fastapi-scaffold/SKILL.md— 完成版
📄lab4-openapi-fastapi-scaffold/requirements.txt— openapi-fastapi-scaffold/requirements.txt

第一輪:純手刻,跑兩次

  1. 先不要複製任何 SKILL.md,也不要裝工具。開一個新的 Agent mode session,提供 meeting-portal-api.yaml,下指令(為了時間,只做兩個 endpoint):

    依照這份 OpenAPI 規格,不要使用任何 code generation 工具,直接手寫 getMeetingSummary 和 getActionItems 這兩個 endpoint 的 FastAPI router 跟對應的 Pydantic model,輸出到 app_llm_run1/ 目錄下。

  2. 開一個全新的 chat session(這步很關鍵——同一個 session 重跑,它會參考自己剛剛的輸出,漂移會被遮住),把同一份規格、同一句指令原封不動再下一次,只把輸出目錄改成 app_llm_run2/。
  3. (選做,想眼見為憑再做)分別啟動兩份輸出,確認兩份都真的能跑——注意 module path 要對到資料夾名稱,而且兩個不能同時佔用同一個 port:
    PowerShell
    python -m uvicorn app_llm_run1.main:app --reload
    PowerShell
    python -m uvicorn app_llm_run2.main:app --reload --port 8001

    如果噴 ModuleNotFoundError,通常是資料夾裡缺 __init__.py(純手刻沒有固定的專案結構,這本身也是一種漂移),補一個空檔案上去即可。這步位可以省略,診斷的重點在下一步的 diff,不是「能不能跑」。

  4. 把兩次輸出互 diff(建議加 --no-pager,不然 PowerShell 預設會丟進 less,卡住要按 q 才能跳出,不是當機):
    PowerShell
    git --no-pager diff --no-index app_llm_run1 app_llm_run2

    看到一堆 __pycache__ 的 binary diff 不用管,那是啟動過 uvicorn 留下的快取,不是 LLM 產出的內容;真正要看的是 .py 檔案本身。如果想單獨聚焦在資料結構,直接只 diff model 檔(通常叫 models.py,依 LLM 這次怎麼命名而定):

    PowerShell
    git --no-pager diff --no-index app_llm_run1/models.py app_llm_run2/models.py

    為什麼特別挑 model 檔看? 因為 main.py(組裝 app)、routers.py(串接哪個 model)差異多半只是措辭、命名習慣這種風格層,不痛不癢;只有 model 檔承載資料結構本身——Optional、Enum、alias 這些欄位定義才是「接前端的人要相信哪一份」的核心。

  5. 全班對答案:實測下來,兩次純手刻保證會踩到的是命名層級的不一致——例如 enum 類別名一次叫 SentimentEnum 一次叫 Sentiment,member 一次是小寫 positive 一次是大寫 POSITIVE。這聽起來像風格問題,但如果任何一支呼叫端程式碼寫了 Sentiment.positive,換到另一次產出就會直接 AttributeError——兩份「看起來都對」的 model,彼此就是兜不起來。

    規格裡還埋了幾顆型別地雷,運氣不好會直接踩到:

    • nullable(ActionItem.dueDate):Optional[date] / date | None / 直接漏掉;
    • enum(sentiment、priority):一次被做成 Enum class、一次被做成裸 str;
    • date-time(generatedAt):一次是 datetime、一次是 str;
    • camelCase 欄位(meetingId、dueDate):一次有 alias 一次沒有。

    這次班上不一定每組都會踩到全部四類——踩到多少純粹看運氣,但命名不一致這一項幾乎每次都會出現。這正是重點:純手刻連「這次剛好對了」都不能保證下次一樣,不需要每次都翻車,只要有機率翻車,就不該是穩定的工程步驟。

第二輪:包工具的 Skill,也跑兩次

  1. 安裝工具(課前沒裝的現在裝):
    PowerShell
    pip install -r requirements.txt
  2. 把完成版 SKILL.md 複製到 .github/skills/openapi-to-fastapi-scaffold/SKILL.md,快速讀一遍它的步驟:model 那一段不是「請產生 Pydantic model」,而是明確指定呼叫 datamodel-codegen(注意步驟裡帶了 --disable-timestamp——沒有它,產出檔頭會有時間戳,等下的 diff 就不乾淨了)。
  3. 開新 session,下指令(這次做完整規格):

    依照這份 OpenAPI 規格,幫我產生 FastAPI 的 router 骨架跟 Pydantic model,輸出到 app/ 目錄下。

  4. 驗證:啟動後開 http://127.0.0.1:8000/docs,確認 spec 裡所有 endpoint 都在,呼叫任一 endpoint 得到 NotImplementedError(預期行為——骨架正確、邏輯留白):
    PowerShell
    python -m uvicorn app.main:app --reload
  5. 再開一個新 session,同一句指令重跑到 app_verify/,然後 diff 兩次的 model。注意路徑:工具版的 model 檔固定叫 schemas.py,放在 app/models/ 子目錄下,不是 app/models.py(這跟第一輪純手刻的檔案結構不一樣,是刻意的對照——第一輪連檔案結構都可能每次不同,第二輪連子目錄結構都固定):
    PowerShell
    git --no-pager diff --no-index app/models/schemas.py app_verify/models/schemas.py

    這次指令跑完畫面上什麼都不會印出來——這正是預期結果,不是指令下錯。 同一份規格,跑一百次,schemas.py byte-level 一致,連類別名稱、enum member 大小寫都不會像第一輪那樣漂移——因為型別轉換這一段根本不是 LLM 在做,是決定性工具在做;LLM 負責的是流程編排跟 router 慣例,那才是它擅長且風險可控的部分。

  6. 回頭抽查第一輪的地雷:對照 app/models/schemas.py,看 sentiment enum、generatedAt date-time、dueDate nullable 在工具版裡是怎麼被正確處理的,再看你純手刻兩份各自錯在哪。
  7. 最後檢查骨架紀律:有沒有哪個函式被「順手」補上看似合理其實沒根據的邏輯——骨架就該是乾淨的 NotImplementedError,這是這個 Skill 的核心紀律。
✅完成檢核
  • 第一輪:兩份純手刻輸出的 models.py diff 出至少一處命名不一致(類別名或 enum member 大小寫);能說出為什麼這種「看起來都對」的差異,換到呼叫端會直接炸開(AttributeError)。
  • 第一輪(加分):有踩到 nullable / enum 型別 / date-time / camelCase alias 其中一類資料結構差異——沒踩到也沒關係,這代表這次運氣好,不代表下次也會好。
  • 第二輪:Swagger UI 看得到所有 endpoint;所有函式是乾淨骨架;uvicorn 正常啟動;兩次工具版 schemas.py 的 diff 為空。
  • 能用一句話回答:「這個 Skill 裡,哪些部分交給決定性工具、哪些部分交給 LLM,為什麼這樣切?」

帶走的觀念:Skill 不是把 prompt 寫長,而是把「不該生成的部分」從生成裡拿掉。 型別轉換有現成的決定性工具,就包工具;LLM 只做工具做不了的編排與慣例。純手刻不需要「每次都錯」才算不可靠——只要存在「這次跟下次長得不一樣」的機率,它就不該是你信任的工程步驟。M2a 你看到的是格式漂移,今天看到的是同一個模式換了個層次:輕則命名對不上、重則型別對不上——解法同源:把可決定的事變成決定的。
