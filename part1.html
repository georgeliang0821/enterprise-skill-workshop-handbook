📌講義設計原則

「先定終點,再把技術主題掛在功能上」——每個重要觀念,都先讓你親眼看到沒有它會出什麼事,再教解法。 上半場有三次刻意安排的「翻車實驗」:

  1. M2a · 翻車①(兩輪):同一句 prompt,全班的輸出各不相同;加上 AGENTS.md(always-on instructions)之後只收斂一半 → 這說明了為什麼需要 Skill,也劃出 instructions 與 Skill 的邊界。
  2. M3c · 翻車②:環境裡有三個 Skill 之後,刻意用模糊指令觀察它選錯 → 這說明了為什麼 description 要寫對比句。
  3. M3d · 翻車③:三個 Skill 都在,一句複合指令下去,誰先跑、跑不跑、會不會越權動檔案,每次都不一樣 → 這說明了為什麼要用 Custom Agent 收斂角色與工具,並用 Handoff 把「下一步」交回使用者。

「照著步驟做完」的記憶兩週就淡了;「親眼看到它出事」的記憶會跟著你回到自己的專案裡。

M1 · 五種資產分工:Always-on Instructions / Prompt File / Skill / Custom Agent / MCP

這五個是你實際會「建立、存成檔案或設定」的資產。其中四個是可觸發、可叫用的能力,Always-on instructions(AGENTS.md,或 GitHub 專屬的 copilot-instructions.md)則是「一直都在」的底層規則,五者共同構成整組客製化的地基。先用一句話分清楚:

它是什麼 用一句話說
Prompt File 存成檔案、可重複叫用的指令範本 你把常用的「幫這個 PR 產生 release notes」指令存成 .prompt.md,之後每次直接 /release-notes 叫出來,不用重打
Custom Agent 一個聚焦、限縮工具的「人設」 用 @ 明確叫出來的角色,只給它特定工具跟特定指令,讓它專心做一件事(例如只做安全審查、不能改檔案)
Skill 固定情境 + 標準流程 + 判斷邏輯 針對一個明確的情境(例如「拿到會議逐字稿」),寫下標準流程、需要的輸入、判斷規則(什麼算決議、日期怎麼換算)與輸出格式;模型判斷情境相符時自動載入,不同人、不同專案執行結果一致
MCP 外部系統的標準化連接介面 「我跟 Outlook 日曆、Jira 溝通的插頭規格」——把外部系統的功能包成 Agent/Skill 可以呼叫的工具,本身不帶團隊的判斷邏輯
Always-on instructions
(AGENTS.md / copilot-instructions.md)		 一直都在、自動注入的專案層級規則 不用叫、每次請求都自動套用的「repo 預設規矩」——命名規範、安全預設、語言/風格慣例都寫這裡,是其他四種資產共用的底層基準

二個最像的:x vs y 逐對拆解

二種可叫用的資產之所以最難分,是因為它們兩兩之間都有一段模糊地帶。以下由「最像」排到「比較好分」,一次看懂邊界。分辨時只要問兩件事:是我喊、還是它自己判斷? 以及 它在管動作、身分、做法、還是連線?

①Prompt File vs. Skill 〈最像〉

兩者都是「可重複使用的工作流」,這是最像的地方。差別在誰觸發與帶不帶附件:

Prompt File Skill
觸發 你手動 打 /指令 模型自動發現、按需載入
載入方式 整份一次注入 漸進式:先讀 name+description,相關時才讀全文,附件再按需取用
帶附件 ✗ 就是一段文字(可帶 ${input:xxx} 變數) ✓ 資料夾可含 scripts / templates / 參考檔
檔案 .github/prompts/*.prompt.md .github/skills/<name>/SKILL.md

一句話:要一個「你自己喊、單檔、輕量」的招式 → Prompt File;要一個「模型自己判斷該用、還帶腳本範本」的完整 runbook → Skill。

②Skill vs. MCP

兩個常被當成同一類,其實本質相反——一個是「怎麼做」,一個是「連到哪」:

Skill MCP
負責 這件事該怎麼做的團隊 SOP(判斷層) 怎麼連上外部系統的工具(協定層)
本質 知識/程序 + 本地腳本 運行中的伺服器,提供活的工具/資料
帶團隊判斷? Skill 是 SOP,照著這份共識做,結果才會一致 MCP 是插頭規格——誰都能插,插了之後要幹嘛它不管

一句話 + Lab 3B 的 weekly-followup-planner 就是搭配使用:MCP 負責讀到你本週行事曆的忙碌與空檔;Skill 負責讀到之後——挑出可用空檔、把未結的 Action Item 排進去、決定輸出格式。

M1b · Context Engineering:先看兩個症狀,再對症下藥

M0 的核心命題有三階。第一階「Prompt Engineering」大部份企業都已經做了;第三階「Skill Engineering」是今天的主軸。中間這一階——Context Engineering:控制模型每一次請求「看到什麼」——是多數人跳過的。這一節不教語法清單;先看兩個症狀,再解釋機制,最後才把 # 對症下藥交給你。

症狀一:Agent 必須自行定位檔案

  1. 講師在 Portal 專案裡開著一個跟日期無關的檔案（例如 App.jsx），並在 Agent 模式詢問：「這個專案哪裡在做日期換算？」
  2. 打開 Developer: Show Chat Debug view，檢查第一個 panel/editAgent。測試結果顯示，開啟中的檔案會以 editorContext 提供檔案路徑，但不會自動附上完整原始碼。因此，「開啟檔案」不等於「把檔案內容加入 prompt」。
  3. 繼續查看後續的 runSubagent、grep_search 與 read_file。這些紀錄才顯示 Agent 實際搜尋了什麼、讀取了哪些檔案，以及工具結果如何進入下一次模型請求。回應底下的 references 可以協助確認引用來源，但不能取代完整的工具呼叫紀錄。
  4. 再使用 #file:App.jsx 明確附加檔案並重送相同問題。這次可在 attachments 中看到完整的 App.jsx 內容，證明明確附加與單純開啟檔案是兩種不同的 context 行為。

這次測試中，初始請求包含工作區資訊與目前檔案路徑，但沒有指出日期換算所在的檔案或 symbol。Agent 必須在迴圈中自行選擇搜尋方式、分析搜尋結果並讀取候選檔案。這不只是隨機猜測，而是由初始 context、搜尋查詢、工具結果與每一步的決策共同決定。若已知關鍵檔案，應明確附加；若不知道位置，則應要求 Agent 搜尋整個 codebase，並以函式定義及呼叫路徑驗證結論。

症狀二:不精準的 context 增加探索成本

  1. 新開一個 session，固定模型，送出不含附件的基準問題。點擊或 hover chat 輸入框的 Context Window 使用量指示器，記錄 Context Window、Session Cost、Files 與 Tool Results。
  2. 另開一個全新 session，把 src/ 資料夾拖進 chat，送出相同問題。資料夾附件只會提供路徑與目錄結構，不會把所有檔案全文加入 prompt；Agent 仍須自行搜尋及讀取檔案。本例的日期換算不在 src/，因此這是一個不精準的探索範圍。
  3. 再開一個全新 session，使用 #file 只附加真正包含日期換算的檔案，送出相同問題。這次完整檔案內容會直接進入 request，Agent 可以少做搜尋與讀檔。
  4. 比較三次的 Context Window、Session Cost、Files 與 Tool Results。若要確認差異來源，再打開 Agent Debug Logs → Summary，比較 input tokens、tool calls、cache reuse 與 credits。

本次測試中，附加正確檔案雖然提高了 Files 的占比，卻減少了 Agent 搜尋、讀檔與工具結果所需的 context，因此整體 token 與 credits 反而較低。重點不是「附件越少越省」，而是越早提供正確且最小的 authoritative context，Agent 越不需要花 token 探索錯誤範圍。實際差距仍會受到模型、回答長度、快取與工具決策影響，教學時應將數字視為這次實驗結果，而不是固定比例。

🔑兩個症狀,同一個核心問題

模型只能根據當次請求中的 instructions、訊息、context 與工具結果推理。找錯檔案或多繞路通常表示缺少足夠且精準的任務 context;探索成本偏高則可能來自不相關的歷史、附件、工具定義或工具結果。兩者都與 context 組裝有關,但 AI credits 還會受到模型、回答長度、推理量、工具呼叫與快取命中率影響,不能只歸因於附件大小。

⚠️兩個常見的誤解,對照上表更正

對症下藥:# 引用怎麼對回兩個症狀

顯性引用(第 6 層)是你控制任務來源 context 最直接的方式。你同時也能控制 user message、session 邊界、customizations、可用工具與模型選擇。引用的原則不是「多加幾個比較保險」,而是加入完成任務所需、最小且可信的來源。

但必要性要分層看。Agent mode 本身就會自主搜尋、讀檔、抓網頁,所以多數引用在 agent mode 下是最佳化(省 turn、消歧義、讓輸入可重現),而不是必要條件。真正不可取代的只有一類:agent 根本沒有對等工具可以取得的來源。

區塊 作用 寫不好會怎樣(對照你剛剛在 M2a 看到的)

它的角色是 recovery(選錯之後給 Copilot 一條回頭路),不是 prevention(選前防呆,那是 description 的工作)。

設計方法:Scope / IO

Scope 怎麼抓——優先權判斷,不是只看一句話長短

  1. 工具/寫入權限邊界是否不同(有沒有副作用、要不要額外認證)→ 不同就該拆,不管兩件事是不是永遠一起發生。
  2. 是否永遠嚴格共同觸發、有強依賴順序 → 傾向合併成一個 Skill 裡的多步驟。
  3. 未來會不會被其他情境單獨呼叫 → 前兩者都中性時的 tie-breaker。

用 meeting-summary 實際套一次:

  • 權限邊界:「產生摘要」跟「抽取待辦」都是唯讀逐字稿、不寫外部系統——邊界一樣,不構成拆開理由。
  • 共同觸發:拿到逐字稿,PM 通常同時要摘要(報告用)也要待辦清單(追蹤用)——成立,指向合併。
  • 單獨呼叫:目前看不出來——中性。

所以 meeting-summary 一次輸出四個區塊:摘要、決議、風險、待辦。「一句話講得完」可以當直覺起手式,但不是唯一判準——如果兩件事永遠綁在一起(例如摘要完順便建 Jira 票),句子只是變長,測試照樣通過,卻掩蓋了權限邊界不同的事實。這也是為什麼 M5 的 Jira 整合是獨立 Skill:建票要寫入外部系統、要額外認證,第一條判準就把它擋在外面。

IO 怎麼定

  • 輸入:講清楚來源、格式、必填項;缺了要反問,不要自己假設。這個 Skill 因為要換算待辦到期日,會議日期是必要輸入——「這週五」「下週三」這種相對日期,沒有基準日無法換算(M2a 你已經看過沒有這條規則時會發生什麼事)。
  • 輸出:要可驗收——指定哪些區塊、什麼格式。模糊的輸出等於每次都不一樣,團隊沒辦法把它當「資產」用。

# 會議逐字稿整理 Skill(Meeting Notes Skill)

## ① 適用範圍 / 不適用時改用
- 適用:使用者提供一份會議逐字稿或會議紀錄全文,並要求產生摘要、決議、風險、或待辦事項——四項只要要求其中任何一項,都由這個 Skill 一次處理。
- 不適用:使用者只是「討論某個主題」、沒有提供實際逐字稿內容——直接對話回答就好。
- 不適用:使用者要的是看本週空檔、把未結事項排進去跟進 → 改用 weekly-followup-planner。

## ② 需要的輸入
1. 會議逐字稿全文(必要)。
2. 會議日期(必要)。逐字稿裡的期限常是「這週五」「下週三」這種相對日期,沒有基準日無法換算,缺少時要先反問使用者。
3. (選)與會人員名單。沒有名單對照時,保留逐字稿原始代稱,不要自己編造人名。

## ③ 步驟
1. 通讀全文,辨識主要議題。
2. 萃取「目前狀態」,合併成 3-4 句話的專案進度摘要。
3. 找出所有「明確被拍板同意」的事項列為 Decisions——只有真正拍板的才算,單純討論或提議不算。
4. 找出所有被明確提及、可能影響進度或合規的疑慮,列為 Risks——每一項要對應具體發言,不能是自己推論。
5. 找出所有「A 對 B 明確指派任務」或「某人主動承諾要做某件事」的語句。
6. 對每一筆任務萃取 Owner(實際姓名,不用職稱)、Action(具體動詞+受詞)、Due Date(依②的會議日期換算成 YYYY-MM-DD,完全沒提到期限則標記「未訂」)、Priority(沒有語氣線索一律 Medium)。
7. 同一人多筆任務分開列出,不要合併成一筆。
8. 依 ④ 的格式整理輸出。

## ④ 輸出格式
```markdown
## Meeting Summary
<一段 3-4 句話的專案進度摘要>

## Decisions
1. <決議事項一>
...

## Risks
- <風險項目一>
...

## Action Items
| Owner | Action | Due Date | Priority |
|---|---|---|---|
| <姓名> | <具體任務> | <YYYY-MM-DD 或「未訂」> | <High/Medium/Low> |
```
四個區塊都要有,即使某區塊為空也要明確寫「無」,不要省略整個區塊。
✅完成檢核
  • /skills 偵測得到 meeting-summary;沒點名 Skill 名稱有自動選用。
  • 跟 M2a 的第一次輸出並排比對,四種偏離預期(結構/日期/決議判定/Owner)都被收斂。
  • Decisions 沒有把「討論中」內容誤判成決議;SAP 整合沒有被列進任何區塊(逐字稿明講「先不排進 PoC 範圍」)。
  • Action Items 的 Due Date 都是換算後的實際日期,沒有殘留「這週五」「下週三」。

M3c · 翻車②:誤觸發實測——三個 Skill 互相干擾

現在你的 .github/skills/ 裡有三個 Skill 了。這是今天第一次、也是企業場景裡每天都在發生的情境:selection 不再只有一個候選。

GitHub Copilot 的 Skill selection 是機率性語意匹配——description 不夠具體、沒有清楚的對比詞,多個 Skill 之間就會互相干擾、選錯或選不到。理論講完了,接下來 15 分鐘直接測。

操作(每一句都是新開對話,避免上下文污染):

  1. 模糊指令一:附上 past-action-items.json,只說:「幫我看一下這些 action item」。——三個 Skill 的 description 裡都有 "action item" 這個詞。觀察選中了誰?還是誰都沒選、直接回答?
  2. 模糊指令二:附上 sample-transcript.txt,說:「幫我把會議裡的待辦整理一下,排個計畫」。——「整理待辦」指向 meeting-summary,「排個計畫」同時沾到 wbs-generator(拆解)跟 weekly-followup-planner(排程)。
  3. 模糊指令三:「我下週要跟進這個專案,幫我準備一下」。——沒有任何一個 Skill 的關鍵詞被直接命中,看它會硬選一個、還是不觸發。
  4. 講師收集現場結果:同一句指令,不同人的機器選中的 Skill 很可能不一樣——這本身就是最重要的觀察:selection 是機率性的,description 的工作是把機率分佈收窄,不是給出保證。
  5. 修復回合:挑一句你這邊選錯(或不觸發)的指令,回頭改對應 Skill 的 description——加對比句、加關鍵詞、或把容易誤導的詞拿掉——再測一次,確認行為改變。

改完之後,養成兩個帶得走的習慣:

  • description 用對比句法,不是只堆關鍵詞:「是逐字稿產出的結構化紀錄,不是排程規劃」,而不是單純寫「摘要、逐字稿、summary」。
  • 新增 Skill 時,把新舊 description 一起丟給 Copilot,問「這兩個會不會混淆、什麼情況下會選錯」——不需要自動化互斥檢查,但至少人工過一次這道關。
📌這個實驗跟下半場的關係

企業內部很快會累積 5-10 個以上相似的 Skill,誤觸發從「偶發」變「日常」。下半場 M5 你會撞到同一件事、但賭注是「寫入外部系統」——到時你就會知道為什麼有些 Skill 該直接鎖成只能手動叫。

💡對照組:prompt file 為什麼永遠不會「誤觸發」

三句模糊指令跑完後,再做一件事:附上逐字稿、打 /meeting-quickcheck。它每次都準確執行、每次都只做它那兩件事——因為它根本沒有參與 selection,是你喊它才出現。這就是 Lab 1B 說的「手動叫用才載入」。所以當一個能力「一定要人明確叫、不能被語意猜中」時,你有兩個選擇:寫成 prompt file,或寫成 Skill 但設 disable-model-invocation: true。差別只在要不要帶附件與腳本——下半場的寫入型 Skill 會用到後者。

M3d · 翻車③:Custom Agent——把三個 Skill 組裝成一個會議助手

五種資產裡,Always-on instructions 與 Prompt File(Lab 1B)、Skill(Lab 2、3)、MCP(Lab 3B)你都做過了,只剩 Custom Agent。這不是漏掉——是刻意留到這裡:Custom Agent 的價值是「把能力組裝起來、鎖住工具邊界、把下一步交給人按」,一定要先有能力可組裝才示範得出來。你現在剛好有三個 Skill 跟一個 prompt file。

M3c 讓你看到三個 Skill 並存時 selection 會互相干擾;這一段給第二帖藥。

先撞一次:預設 Agent Mode 的「編排失控」

操作(乾淨對話,三個 Skill 都在):

重點來了:tools 欄位只收工具名(內建工具、tool sets、MCP 工具)——frontmatter 裡沒有任何「Skill 白名單」欄位。Skill 的觸發永遠走 description 語意匹配(M3c 練的那一層),Custom Agent 改變的是「以什麼人設、帶著哪些工具」去做匹配,而不是把其他 Skill 從選單上拿掉。

那 Skill 層有沒有「護欄」?有——但它長在 SKILL.md 自己身上,就是 M2b 認識過的 disable-model-invocation: true(該 Skill 從此只能手動 /skill-name 叫用,不會被任何 agent 自動選中)。所以完整的治理拼圖是:工具的護欄蓋在 agent 上,Skill 的護欄蓋在 Skill 上,行為準則寫在 agent 的 body 裡。記住這張拼圖——下半場你會遇到一個 tools 白名單管不到、只能靠 Skill 自己這道護欄的場景。

🔑這一帖藥跟 M3c 的差別

M3c 的 description 對比句,收的是「哪個 Skill 被選中」的機率。Custom Agent 的路由規則,收的是「這個角色會怎麼編排」的機率——固定人設 + 明確路由,讓同一句複合指令每次走同一條路。而 tools 白名單處理的是另一個維度:就算路由漂了,它能造成的傷害被護欄限制住。三個槓桿疊加使用——description(M3c)、路由指令(現在)、工具邊界(現在)——不是三選一。

# 會議營運助手(Meeting Ops Agent)

你是會議逐字稿的下游營運助手。你**不自己發明「怎麼做」**——所有實際產出都交給對應的
Skill,你只負責路由、補齊必要輸入、守住邊界。

## 路由規則(薄路由,不重寫 SOP)
你只使用以下三個 Skill,除此之外的 Skill 一律不採用:
- 給逐字稿、要摘要/決議/風險/待辦 → 使用 meeting-summary
- 要把範圍拆成 WBS / Excel          → 使用 wbs-generator
- 問「本週哪些時段有空、把未結事項排進去」→ 使用 weekly-followup-planner
- 一句話同時要「整理+排計畫」時,先做 meeting-summary,再把產出的 Action Items
  交給 weekly-followup-planner,並向使用者說明你的順序。
- 缺會議日期時先反問(延續 meeting-summary ② 的必要輸入),不要自己假設。

## 邊界(能碰什麼/不能碰什麼)
- 只在會議產出範圍內工作;不修改 Portal 應用程式原始碼。
- 需要寫入外部系統(例如建 Jira 票)時,明講超出範圍、交還使用者,不要自己找工具硬做。

02 / 06 — description 這行字,到底寫給誰看?

meeting-ops 是 @ 手動叫出來的,這種情況下 description 的閱聽眾是人——它只出現在下拉選單、輸入框的 placeholder 文字裡,幫你或同事判斷「這是不是我要的角色」,寫成人話就好,不用刻意塞觸發關鍵詞。

🧱但如果哪天它被掛進更大的編排,閱聽眾會換人

Custom Agent 可以被另一個 agent 當成 subagent 呼叫。這種情境下,決定「該不該選中它」的不再是人眼掃過下拉選單,而是模型讀 description 來判斷——跟 SKILL.md 的 description 是同一種機制:要包含「做什麼、何時該選我」。今天的骨架只走純手動叫用這條路,所以現在不用改寫法;但理解這個切換點,是看懂下一節「subagent 授權」在防什麼的前提。

03 / 06 — 你的 agent 會不會被拉去當 subagent?

一個常見誤解:「我的 .agent.md 裡沒寫 agents 欄位,所以沒有人可以呼叫到我」——方向反了。agents 欄位是寫在呼叫者身上的允許清單,不是寫在被呼叫者身上的門禁。

⚠️預設值是開放的

只要你沒有主動設 disable-model-invocation: true,你的 agent 就預設可以被任何有 agent tool、且把它列進自己 agents 陣列(或用 *)的 coordinator agent 當成 subagent 呼叫。「沒寫 agents 欄位」跟「不會被呼叫」完全是兩件事。

你想要的結果 該怎麼設 設在誰身上
預設行為:可以被任何 coordinator 呼叫 什麼都不用寫 —
完全不能被當 subagent,只能 @ 手動叫 disable-model-invocation: true 寫在自己的 .agent.md
平常鎖死,但某個信任的 coordinator 仍可呼叫 自己設 disable-model-invocation: true,coordinator 的 agents 陣列明確列出你的名字 兩邊都要設

最後一列的關鍵細節:被明確列進 agents 陣列,會覆蓋它自己的 disable-model-invocation: true——這是「預設鎖死、對信任對象開白名單放行」的設計,跟今天 tools 白名單的邏輯是同一種精神,只是防的方向不同:tools 防「meeting-ops 能碰什麼工具」,這裡防「meeting-ops 會不會被其他 agent 拉去用」。

04 / 06 — tools 白名單:不要背拼法,用工具選單勾

tools 的合法值是內建工具、tool sets、MCP 工具(整個 MCP server 用 <server 名>/*)。填了不存在的名稱不會報錯,只會被靜默忽略——這是最危險的失效模式:你以為蓋了護欄,其實沒有。

正確做法不是背拼法,而是在 Agent Customizations editor(Chat 齒輪 → Agents)裡編輯 agent 時,用工具勾選清單產生名稱;骨架裡的 'edit'、'runCommands' 以你環境實際顯示的為準。

⚠️tools 裡的 MCP 工具名 = mcp.json 的 server key,不是工具本身的名字

最容易對不到的就是 MCP 工具。tools 認的是你 mcp.json 裡 servers 底下那個 key,命名慣例是 <server-name>/<tool-name>(整個 server 全放行就用 <server-name>/*)。

jsonc
// .vscode/mcp.json
"servers": {
  "agent365-calendartools": { /* ... */ },   // ← server-name 就是這個 key
  "microsoft-learn":         { /* ... */ },
  "github":                  { /* ... */ }
}

要放行整個行事曆 server,寫的是 agent365-calendartools/*。若只寫 agent365-calendartools(少了 /),就不符合 server/tool 慣例——就算它剛好跟某個工具同名,也對不到任何「內建工具、別名、或 server/tool pattern」,一樣被靜默忽略。這正是「假護欄」:名字沒填對,護欄根本沒蓋起來,而且不會報錯。實務上別手打,用 VS Code 的工具勾選清單產生名稱。

定義一次、引用多次:Tool sets

到 M5 結束你會有四個 agent。每一個都在工具選單勾同一組七、八個 checkbox,既慢又容易漏。VS Code 的 tool set 讓你把一組工具取一個名字:執行 Chat: Configure Tool Sets 建立設定檔,定義例如 meeting-tools = edit + CalendarTools/* + 讀檔搜尋;之後在 .agent.md 的 tools: 裡寫 meeting-tools,或在 prompt 裡打 #meeting-tools,一次帶進整組。

⚠️tool set 是使用者層級設定,不進 repo——這是另一種「假護欄」

依目前文件,tool set 定義檔存在你的使用者設定裡,不隨 repo 走。所以 .agent.md 寫了 meeting-tools、同事 clone 下來卻沒有這個 tool set → 名稱被靜默忽略,跟填錯拼法一樣,你以為蓋了牆,他那邊沒有。也是下半場 M8' 要講的「拆散的 bundle」的另一個案例。本課的立場:開發期用 tool set 省手;交付的 .agent.md 把 tools 展開成明確工具名(或在 bundle 說明裡附上 tool set 定義)。

三個最常見的錯誤

  • 別把 SOP 抄進 agent:一旦把「怎麼做」複製進 .agent.md,就跟 Skill 重複、日後兩邊不同步——正是 M1 警告過的反例。Agent 裡只放路由,不放步驟。

05b / 06 — Subagent:把繁雜的工作派出去,把危險的工具一起帶走

用 @meeting-ops 下「整理這場會議,並把 PoC 拆成 WBS」,看主對話:wbs-generator 會寫一段 Python、呼叫終端機、可能報錯重跑——這些 tool output 全部進了主對話的 context(M1b 七層表的第 7 層)。看一眼 context window 指示器,再對照只做摘要時的數字。這就是症狀二在 agent 層的長相。

Custom Agent 可以把一部分工作派給另一個 custom agent 當 subagent 執行:subagent 在自己的 context 裡跑完整個 agentic loop,只把結果摘要回傳給呼叫者;而且它帶自己的 tools 白名單。兩件事一起成立,就出現一個有意思的機會:

🔑WBS 派給 subagent 之後,@meeting-ops 自己就不再需要 runCommands

⚠️handoff 的兩個現實
  • send: true 會自動送出預填 prompt——那就變回「模型接著跑」,只是換了個 agent。要人審核的下一步一律 send: false。
  • handoff 是 VS Code chat 的 UI 機制;在 Copilot CLI 與雲端 coding agent 裡的支援程度以當天版本為準(下半場 M6' 會實際看)。這也是為什麼「真正的護欄要長在 Skill 自己身上」(disable-model-invocation)——它走到哪都在,handoff 不一定。
