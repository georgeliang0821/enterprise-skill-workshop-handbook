提出解法前的誠實時刻:Custom Agent 鎖得住什麼、鎖不住什麼

🔑一護欄一行為準則:兩種完全不同強度的收斂

依照目前 GitHub Copilot 的 .agent.md 規格,Custom Agent 給你的是兩種強度不同的收斂手段,千萬不要混為一談:

工具邊界(護欄) Skill 路由(行為準則)
靠什麼 frontmatter 的 tools 白名單 body 裡的路由指令(instructions)
強度 結構保證:不在清單上的工具,物理上叫不到 機率收斂:大幅縮小注意力範圍,但不是白名單
管什麼 危險的(寫檔、跑終端、外部系統) 選擇的(該用哪個 Skill、什麼順序)
失效模式 填錯工具名 → 被靜默忽略、不報錯(以為有護欄其實沒護欄) 指令寫得含糊 → 路由照樣漂

重點來了:tools 欄位只收工具名(內建工具、tool sets、MCP 工具)——frontmatter 裡沒有任何「Skill 白名單」欄位。Skill 的觸發永遠走 description 語意匹配(M8 練的那一層),Custom Agent 改變的是「以什麼人設、帶著哪些工具」去做匹配,而不是把其他 Skill 從選單上拿掉。

那 Skill 層有沒有「護欄」?有——但它長在 SKILL.md 自己身上,就是 M6 認識過的 disable-model-invocation: true(該 Skill 從此只能手動 /skill-name 叫用,不會被任何 agent 自動選中)。所以完整的治理拼圖是:工具的護欄蓋在 agent 上,Skill 的護欄蓋在 Skill 上,行為準則寫在 agent 的 body 裡。記住這張拼圖——M11 你會遇到一個 tools 白名單管不到、只能靠 Skill 自己這道護欄的場景。

🔑這一帖藥跟 M8 的差別

M8 的 description 對比句,收的是「哪個 Skill 被選中」的機率。Custom Agent 的路由規則,收的是「這個角色會怎麼編排」的機率——固定人設 + 明確路由,讓同一句複合指令每次走同一條路。而 tools 白名單處理的是另一個維度:就算路由漂了,它能造成的傷害被護欄限制住。三個槓桿疊加使用——description(M8)、路由指令(現在)、工具邊界(現在)——不是三選一。

提出解法:一個「編排型」Custom Agent

設計原則直接沿用 M1 立好的兩句話:Custom Agent 定義「誰+能碰什麼」,Skill 定義「怎麼做」;而且 Agent 只做薄路由,真正怎麼做的邏輯留在 Skill。所以這個 agent 刻意不含任何 SOP——它只判斷該叫哪個 Skill、補齊缺的必要輸入、守住工具邊界。

# 會議營運助手(Meeting Ops Agent)

你是會議逐字稿的下游營運助手。你**不自己發明「怎麼做」**——所有實際產出都交給對應的
Skill,你只負責路由、補齊必要輸入、守住邊界。

## 路由規則(薄路由,不重寫 SOP)
你只使用以下三個 Skill,除此之外的 Skill 一律不採用:
- 給逐字稿、要摘要/決議/風險/待辦 → 使用 meeting-summary
- 要把範圍拆成 WBS / Excel          → 使用 wbs-generator
- 問「本週哪些時段有空、把未結事項排進去」→ 使用 weekly-followup-planner
- 一句話同時要「整理+排計畫」時,先做 meeting-summary,再把產出的 Action Items
  交給 weekly-followup-planner,並向使用者說明你的順序。
- 缺會議日期時先反問(延續 meeting-summary ② 的必要輸入),不要自己假設。

## 邊界(能碰什麼/不能碰什麼)
- 只在會議產出範圍內工作;不修改 Portal 應用程式原始碼。
- 需要寫入外部系統(例如建 Jira 票)時,明講超出範圍、交還使用者,不要自己找工具硬做。

@meeting-ops 從骨架到能用，中間有六個容易踩空的細節——存哪裡、叫誰、description 寫給誰看、tools 怎麼填才不會蓋出「假護欄」。以下拆成五個決策點,並用兩個符號貫穿全程;第六、七個——Subagent 與 Handoff——是 M10。

② description 這行字,到底寫給誰看?

meeting-ops 是 @ 手動叫出來的,這種情況下 description 的閱聽眾是人——它只出現在下拉選單、輸入框的 placeholder 文字裡,幫你或同事判斷「這是不是我要的角色」,寫成人話就好,不用刻意塞觸發關鍵詞。

🧱但如果哪天它被掛進更大的編排,閱聽眾會換人

Custom Agent 可以被另一個 agent 當成 subagent 呼叫。這種情境下,決定「該不該選中它」的不再是人眼掃過下拉選單,而是模型讀 description 來判斷——跟 SKILL.md 的 description 是同一種機制:要包含「做什麼、何時該選我」。今天的骨架只走純手動叫用這條路,所以現在不用改寫法;但理解這個切換點,是看懂下一節「subagent 授權」在防什麼的前提。

③ 你的 agent 會不會被拉去當 subagent?

一個常見誤解:「我的 .agent.md 裡沒寫 agents 欄位,所以沒有人可以呼叫到我」——方向反了。agents 欄位是寫在呼叫者身上的允許清單,不是寫在被呼叫者身上的門禁。

⚠️預設值是開放的

只要你沒有主動設 disable-model-invocation: true,你的 agent 就預設可以被任何有 agent tool、且把它列進自己 agents 陣列(或用 *)的 coordinator agent 當成 subagent 呼叫。「沒寫 agents 欄位」跟「不會被呼叫」完全是兩件事。

你想要的結果 該怎麼設 設在誰身上
預設行為:可以被任何 coordinator 呼叫 什麼都不用寫 —
完全不能被當 subagent,只能 @ 手動叫 disable-model-invocation: true 寫在自己的 .agent.md
平常鎖死,但某個信任的 coordinator 仍可呼叫 自己設 disable-model-invocation: true,coordinator 的 agents 陣列明確列出你的名字 兩邊都要設

最後一列的關鍵細節:被明確列進 agents 陣列,會覆蓋它自己的 disable-model-invocation: true——這是「預設鎖死、對信任對象開白名單放行」的設計,跟今天 tools 白名單的邏輯是同一種精神,只是防的方向不同:tools 防「meeting-ops 能碰什麼工具」,這裡防「meeting-ops 會不會被其他 agent 拉去用」。

④ tools 白名單:不要背拼法,用工具選單勾

tools 的合法值是內建工具、tool sets、MCP 工具(整個 MCP server 用 <server 名>/*)。填了不存在的名稱不會報錯,只會被靜默忽略——這是最危險的失效模式:你以為蓋了護欄,其實沒有。

正確做法不是背拼法,而是在 Agent Customizations editor(Chat 齒輪 → Agents)裡編輯 agent 時,用工具勾選清單產生名稱;骨架裡的 'edit'、'runCommands' 以你環境實際顯示的為準。

⚠️tools 裡的 MCP 工具名 = mcp.json 的 server key,不是工具本身的名字

最容易對不到的就是 MCP 工具。tools 認的是你 mcp.json 裡 servers 底下那個 key,命名慣例是 <server-name>/<tool-name>(整個 server 全放行就用 <server-name>/*)。

jsonc
// .vscode/mcp.json
"servers": {
  "agent365-calendartools": { /* ... */ },   // ← server-name 就是這個 key
  "microsoft-learn":         { /* ... */ },
  "github":                  { /* ... */ }
}

要放行整個行事曆 server,寫的是 agent365-calendartools/*。若只寫 agent365-calendartools(少了 /),就不符合 server/tool 慣例——就算它剛好跟某個工具同名,也對不到任何「內建工具、別名、或 server/tool pattern」,一樣被靜默忽略。這正是「假護欄」:名字沒填對,護欄根本沒蓋起來,而且不會報錯。實務上別手打,用 VS Code 的工具勾選清單產生名稱。

定義一次、引用多次:Tool sets

到 M11 結束你會有四個 agent。每一個都在工具選單勾同一組七、八個 checkbox,既慢又容易漏。VS Code 的 tool set 讓你把一組工具取一個名字:執行 Chat: Configure Tool Sets 建立設定檔,定義例如 meeting-tools = edit + CalendarTools/* + 讀檔搜尋;之後在 .agent.md 的 tools: 裡寫 meeting-tools,或在 prompt 裡打 #meeting-tools,一次帶進整組。

⚠️tool set 是使用者層級設定,不進 repo——這是另一種「假護欄」

依目前文件,tool set 定義檔存在你的使用者設定裡,不隨 repo 走。所以 .agent.md 寫了 meeting-tools、同事 clone 下來卻沒有這個 tool set → 名稱被靜默忽略,跟填錯拼法一樣,你以為蓋了牆,他那邊沒有。這也是「agent + 它路由的 Skill + 它用的 tool set 是一組,不能拆開搬」的一個案例——M13 把資產搬到 CLI 時會再提醒一次。本課的立場:開發期用 tool set 省手;交付的 .agent.md 把 tools 展開成明確工具名(或在 bundle 說明裡附上 tool set 定義)。

三個最常見的錯誤

  • 別把 SOP 抄進 agent:一旦把「怎麼做」複製進 .agent.md,就跟 Skill 重複、日後兩邊不同步——正是 M1 警告過的反例。Agent 裡只放路由,不放步驟。
  • 別以為沒寫 agents 欄位就沒人能呼叫你:agents 欄位是呼叫者的允許清單,不是你的門禁。真的要防被拉去當 subagent,得自己設 disable-model-invocation: true。
  • Custom Agent 不是 selection 正確性的保證:路由規則是強力行為準則,但 description 對比句(M8 練的)還是要寫好——行為準則與機率收斂疊加,才有穩定行為。

M10 · Subagent 與 Handoff:把繁雜的工作派出去,把「下一步」交給人按

@meeting-ops 現在會路由、有工具邊界。這一段解兩件它還沒解的事:WBS 那一段的終端機工作全部進了主對話的 context,而且 @meeting-ops 因此得留著 runCommands;「先整理,再排進本週」這條線現在是模型自己決定要不要接著跑。前者用 subagent,後者用 handoff——兩者都是 M9 那兩種收斂強度的延伸。

Subagent:把繁雜的工作派出去,把危險的工具一起帶走

Custom Agent 可以把一部分工作派給另一個 custom agent 當 subagent 執行:subagent 在自己的 context 裡跑完整個 agentic loop,只把結果摘要回傳給呼叫者;而且它帶自己的 tools 白名單。兩件事一起成立,就出現一個有意思的機會:

🔑WBS 派給 subagent 之後,@meeting-ops 自己就不再需要 runCommands

M12 · 翻車⑤:OpenAPI → FastAPI Scaffolding——型別漂移(講師示範)+ applyTo instructions

這是今天技術密度最高的一段,對應企業導入 Copilot 最常見的具體需求:「從 API Spec 產生 Controller 骨架」。而這份規格就是 Portal 自己的後端 API——做完這一步,M0 demo 裡的前端終於有真正的後端可以接,故事線閉環。

🔑本堂最重要的一個觀念

最穩的 scaffolding Skill,通常不是叫 LLM 純手寫,而是讓步驟去「包一個既有的決定性工具」、再疊上團隊規範與品質自檢。這裡用 datamodel-codegen 從 OpenAPI 規格產生 Pydantic model,Skill 負責「呼叫工具 + 套 router 慣例 + 自檢」。

這句話今天不用你相信——講師會把對照組投影出來:同一份規格純手刻兩次的 diff;然後你自己用包工具的 Skill 跑,看它為什麼穩。你在上半場 M3 已經看過偏離預期這個模式,只是這次換了一個層次:輕則類別命名、enum member 大小寫不一致(換一次產出,呼叫端的 Sentiment.positive 可能直接 AttributeError),重則型別本身對不上——不是格式難看那種一眼看得出來的偏離,是「兩份看起來都對,但兜不起來」的型別漂移。

適用前提:這個做法假設 OpenAPI spec 已經定案(治理委員會審過、或對外合約規格)。

設計題 我們的決定
Scope(一句話) 「給我 OpenAPI 規格,我給你 FastAPI 的 router 骨架 + Pydantic model」
