# 會議營運助手(Meeting Ops Agent)

你是會議逐字稿的下游營運助手。你**不自己發明「怎麼做」**——所有實際產出都交給對應的
Skill,你只負責路由、補齊必要輸入、守住邊界。

## 路由規則(只負責判斷該找誰做事,不重寫 SOP)
你只使用以下三個 Skill,除此之外的 Skill 一律不採用:
- 給逐字稿、要摘要/決議/風險/待辦 → 使用 meeting-summary
- 要把範圍拆成 WBS / Excel          → 使用 wbs-generator
- 要替 WBS / 工作項逐項查證技術依據    → 使用 tech-grounding-checker
- 一句話同時要「拆 WBS + 查證」時,先做 wbs-generator,再把產出的工作項
  交給 tech-grounding-checker,並向使用者說明你的順序。   # ← 刻意保留:M10 v3 會刪掉這條
- 缺會議日期時先反問(延續 meeting-summary ② 的必要輸入),不要自己假設。

## 邊界(能碰什麼/不能碰什麼)
- 只在會議產出範圍內工作;不修改 Portal 應用程式原始碼。
- 需要寫入外部系統(例如建 Jira 票)時,明講超出範圍、交還使用者,不要自己找工具硬做。
⚠️read 不能省——不然你的 Skill 等於沒寫

Skill 是漸進揭露的:frontmatter 只給 agent 一行 description,真正的 SOP 全在 SKILL.md 裡。agent 必須實際去讀那個檔,SOP 才會生效。

把 read 從白名單拿掉,會發生兩件事,而且都不報錯:

  • 它繞去終端機下 Get-Content SKILL.md;你按 Allow 就過,按 Skip 就卡死。
  • 更糟的情況:它乾脆不讀,直接憑模型的常識生一份。摘要照樣出來、看起來也像回事,但四區塊格式、Action Items 表格欄位、命名規則全部沒套用——你要把兩次輸出並排才看得出來 Skill 根本沒被打開過。

規則:任何會用到 Skill 的 agent,tools 一定要有 read。這條規則等一下的 wbs-builder 和 grounding-checker 同樣適用。

寫這個檔案時你會做三個決定:存哪裡、description 寫給誰看、tools 怎麼填。前兩個各藏著一個「選錯不會報錯」的無聲陷阱——這是 Custom Agent 最容易讓人誤以為「已經設好了」的地方。

② description 這行字,寫給誰看?

meeting-ops 是從 Agents 下拉選單手動切換的角色,description 會顯示成輸入框的 placeholder 文字,幫你或同事確認「這是不是我要的角色」。所以它的第一讀者是人,寫成人話就好。

但要注意:Custom Agent 預設就能被其他 agent 當 subagent 呼叫(disable-model-invocation 預設為 false)。

📐預告:閱聽眾會換人的那一天

一旦允許被當成 subagent 呼叫,決定「該不該選中它」的就是模型讀 description,跟 SKILL.md 的 description 是同一種機制,要寫清楚「做什麼、何時該選我」。M10 v2 建 wbs-builder 時就會用到;反過來,如果某個 agent 只想給 subagent 用、不想出現在選單,則設 user-invocable: false。

③ 🧱 tools 白名單:本段唯一的護欄

tools 的合法值是內建工具與 MCP 工具(整個 MCP server 用 <server 名>/*)。v1 需要的是:read(讀 SKILL.md)、edit(寫摘要與 Excel)、execute(wbs-generator 跑 Python)、microsoft-learn/*(查證)。九類內建工具各自在做什麼,見附錄 · Built-in 工具一覽。

MCP 工具的 server 名,就是你 .vscode/mcp.json 裡的 key:

jsonc
// .vscode/mcp.json
"servers": {
  "microsoft-learn": { /* ... */ },   // ← server-name 就是這個 key(上半場 Lab 7B 設的)
  "github":          { /* ... */ }
}
📐工具選單裡每一類左邊的 >,是可以展開的

edit、execute 這些不是單一工具,是一類子工具。展開 execute 你會看到 runInTerminal、runTask、runTests、runNotebookCell 等等;勾整類就是全部放行。v1 先勾整類求快,M10 v2 會回來把 execute 削到只剩一項——那才是工具邊界真正收緊的一刻。子工具清單見附錄 · 子工具:把一類削成一項。

⚠️無聲陷阱 2/2:工具名填錯,護欄根本沒蓋起來

填了不存在的名稱不會報錯,只會被靜默忽略——你以為蓋了護欄,其實沒有。常見兩種:

  • 放行整個 Learn server 要寫 microsoft-learn/*;只寫 microsoft-learn(少了 /*)對不到任何「內建工具、別名、或 server/tool pattern」,一樣被忽略。
  • 內建工具名會隨 VS Code 版本改名(例如終端機工具,舊文件或舊版可能寫 runCommands,新版選單顯示 execute)。照著舊教材手打,就可能打到一個已不存在的名字。

不要背拼法:在 Agent Customizations editor(Chat 齒輪 → Agents)編輯 agent 時,用工具勾選清單產生名稱。本課骨架裡的工具名,以你當天環境實際顯示的為準。

同一個 agent、同一次設定,兩個要求卻由不同強度的東西處理。把這兩道牆的性質攤開:

🔑一護欄一行為準則:兩種完全不同強度的收斂

三個最常見的錯誤

  • 別把 SOP 抄進 agent:一旦把「怎麼做」複製進 .agent.md,就跟 Skill 重複、日後兩邊不同步——正是 M1 警告過的反例。Agent 裡只放路由,不放步驟。
  • 別以為寫了就有護欄:scope 選錯、工具名填錯都不會報錯。護欄要用「測一次叫不叫得到」來驗證,不是用「我有寫」來驗證——就像你剛剛跑 T4 那樣。
  • Custom Agent 不是 selection 正確性的保證:路由規則是強力行為準則,但 description 對比句(M6 / M7 寫的)還是要寫好——疊加才有穩定行為。

這三件事的共同解法,是換人:把需要終端機的那段工作交給另一個 agent(v2),把需要審核的下一步交給人(v3)。

v2 · Subagent:把繁雜的工作派出去,把危險的工具一起帶走

Custom Agent 可以把一部分工作派給另一個 custom agent 當 subagent 執行:subagent 在自己的 context 裡跑完整個 agentic loop,只把結果摘要回傳給呼叫者;而且它帶自己的 tools 白名單。

🔑下放的價值,在於下放的同時把權限削小

把 wbs-generator 放進 wbs-builder subagent,@meeting-ops 的 tools 就可以拿掉 execute。但如果把整類 execute 原封不動搬過去,你只是換了持有人,沒換權限。四件事一起做,這一步才算數:

  1. 把需要危險工具的那段工作獨立成一個 subagent
  2. 呼叫者的 tools 拿掉該工具,並用 agents 限定只能派給它
  3. subagent 只勾那段工作實際用得到的子工具
  4. subagent 設 user-invocable: false,從下拉選單消失,只能被派工、不能被直接選來對話

驗收標準只有一句:使用者能選到的每一個 agent,身上都沒有終端機。終端機只存在於「meeting-ops → wbs-builder」這一條被白名單限定的路徑上。少了第 4 件,使用者直接在選單選 wbs-builder,就又多了一個握著 shell 的入口。

# FastAPI 慣例(處理 app/ 與 tests/ 底下檔案時套用)

## 骨架階段
- 每個 OpenAPI tag 一個 router 檔:app/routers/.py;每個 operationId 一個函式。
- Pydantic model 只放在 app/models/schemas.py,router 不得自行定義 model。
- 函式體只能是 `raise NotImplementedError("")`,不得補上猜測的商業邏輯。

## 實作階段
- 每個 router 必須有對應的 tests/test_.py,用 FastAPI TestClient。
- 每個測試檔至少涵蓋一個成功狀態碼(200 或 201)與一個 4xx;
  spec 沒有定義 4xx 的 endpoint,用 FastAPI 的 422 驗證錯誤(例如 /search 不帶 q)。
- stub 只回傳符合 response_model 的假資料,不得自行補上規格沒有的商業邏輯。

## 兩個階段都適用
- 不要修改 app/models/schemas.py——它是由 datamodel-codegen 產生的,改規格請改 openapi/*.yaml 後重跑。
💡兩個細節值得多看三秒

① glob 要蓋到「規則管的所有路徑」。 測試那條規則管的是 tests/,所以 glob 不能只寫 app/**——不然 agent 在建 tests/test_meetings.py 的時候,這份檔案根本不會被注入。規則寫給誰看,glob 就要蓋到誰。

② 這份檔案裡有一半的規則,今天會被載入、但用不上。 「實作階段」那一段在 M12 也會跟著注入——只是今天的任務只產骨架,不寫 stub、不建測試,那些規則沒有東西可以約束。它真正派上用場是在 M14 的雲端 agent,因為那時的任務才碰得到它。

再多埋一個伏筆:仔細看「骨架階段」第三條跟「實作階段」第三條——一條說函式體只能 raise,一條說要回假資料。今天你在場,不會混淆;但 M14 派出去之後你就不在場了。M14 派任務之前,你會回來修這裡。

spec 裡長這樣 兩次產出常見的分歧 踩到會怎樣
sentiment: [positive, neutral, negative] 類別名 Sentiment / SentimentEnum;member 大小寫不一 呼叫端 Sentiment.positive 換一份就 AttributeError

🔑本段最重要的一個觀念:可信度的來源換了

容易混淆的兩組:web 是「讀」網頁、browser 是「操作」網頁;execute 能跑任何指令,權限最大。勾得越少,agent 行為越可控——但 read 不能省,少了它 Skill 的 SOP 根本不會被讀到。

子工具:把一類削成一項

九類每一類左邊的 > 展開後是子工具清單,可以逐項勾。子工具名稱寫進 tools: 時會取代整類名稱——勾了 execute 底下的 runInTerminal,tools: 裡出現的就是 runInTerminal,不再是 execute。

🔑先削 execute,edit 有時間再說

edit 動的是你自己 workspace 裡的檔案,最壞情況是改壞一個檔,有 git 可以救。execute 動的是整台機器——裝套件、刪檔案、打外部 API 都在這一類底下。投資報酬差很多,時間有限就只削 execute。

但也別高估它:沒勾 runTests 攔不住 pytest,因為 runInTerminal 本來就能打任何指令。削子工具拿掉的是「額外的入口」,不是「終端機本身的能力」。真正的下一層護欄在 M11。
