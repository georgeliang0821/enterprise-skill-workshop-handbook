# 會議營運助手(Meeting Ops Agent)

你是會議逐字稿的下游營運助手。你**不自己發明「怎麼做」**——所有實際產出都交給對應的
Skill,你只負責路由、補齊必要輸入、守住邊界。

## 路由規則(只負責判斷該找誰做事,不重寫 SOP)
你只使用以下三個 Skill,除此之外的 Skill 一律不採用:
- 給逐字稿、要摘要/決議/風險/待辦 → 使用 meeting-summary
- 要把範圍拆成 WBS / Excel          → 使用 wbs-generator
- 要替 WBS / 工作項逐項查證技術依據    → 使用 tech-grounding-checker
- 一句話同時要「拆 WBS + 查證」時,先做 wbs-generator,再把產出的工作項
  交給 tech-grounding-checker,並向使用者說明你的順序。   # ← 刻意保留:M10 v3 會刪掉這條
- 缺會議日期時先反問(延續 meeting-summary ② 的必要輸入),不要自己假設。

## 邊界(能碰什麼/不能碰什麼)
- 只在會議產出範圍內工作;不修改 Portal 應用程式原始碼。
- 需要寫入外部系統(例如建 Jira 票)時,明講超出範圍、交還使用者,不要自己找工具硬做。
⚠️read 不能省——不然你的 Skill 等於沒寫

Skill 是漸進揭露的:frontmatter 只給 agent 一行 description,真正的 SOP 全在 SKILL.md 裡。agent 必須實際去讀那個檔,SOP 才會生效。

把 read 從白名單拿掉,會發生兩件事,而且都不報錯:

  • 它繞去終端機下 Get-Content SKILL.md;你按 Allow 就過,按 Skip 就卡死。
  • 更糟的情況:它乾脆不讀,直接憑模型的常識生一份。摘要照樣出來、看起來也像回事,但四區塊格式、Action Items 表格欄位、命名規則全部沒套用——你要把兩次輸出並排才看得出來 Skill 根本沒被打開過。

規則:任何會用到 Skill 的 agent,tools 一定要有 read。這條規則等一下的 wbs-builder 和 grounding-checker 同樣適用。

寫這個檔案時你會做三個決定:存哪裡、description 寫給誰看、tools 怎麼填。前兩個各藏著一個「選錯不會報錯」的無聲陷阱——這是 Custom Agent 最容易讓人誤以為「已經設好了」的地方。

② description 這行字,寫給誰看?

meeting-ops 是 @ 手動叫出來的,這種情況下 description 的閱聽眾是人:它只出現在下拉選單、輸入框的 placeholder 文字裡,幫你或同事判斷「這是不是我要的角色」。寫成人話就好,不用刻意塞觸發關鍵詞。

Custom Agent 也能被另一個 agent 當成 subagent 呼叫。那時決定「該不該選中它」的是模型讀 description,跟 SKILL.md 的 description 是同一種機制,要寫清楚「做什麼、何時該選我」。v1 只走手動叫用,現在不用改;M10 v2 建 wbs-builder 時就會用到。

③ 🧱 tools 白名單:本段唯一的護欄

tools 的合法值是內建工具與 MCP 工具(整個 MCP server 用 <server 名>/*)。v1 需要的是:read(讀 SKILL.md)、edit(寫摘要與 Excel)、execute(wbs-generator 跑 Python)、microsoft-learn/*(查證)。九類內建工具各自在做什麼,見附錄 · Built-in 工具一覽。

MCP 工具的 server 名,就是你 .vscode/mcp.json 裡的 key:

jsonc
// .vscode/mcp.json
"servers": {
  "microsoft-learn": { /* ... */ },   // ← server-name 就是這個 key(上半場 Lab 7B 設的)
  "github":          { /* ... */ }
}
📐工具選單裡每一類左邊的 >,是可以展開的

edit、execute 這些不是單一工具,是一類子工具。展開 execute 你會看到 runInTerminal、runTask、runTests、runNotebookCell 等等;勾整類就是全部放行。v1 先勾整類求快,M10 v2 會回來把 execute 削到只剩一項——那才是工具邊界真正收緊的一刻。子工具清單見附錄 · 子工具:把一類削成一項。

⚠️無聲陷阱 2/2:工具名填錯,護欄根本沒蓋起來

填了不存在的名稱不會報錯,只會被靜默忽略——你以為蓋了護欄,其實沒有。常見兩種:

  • 放行整個 Learn server 要寫 microsoft-learn/*;只寫 microsoft-learn(少了 /*)對不到任何「內建工具、別名、或 server/tool pattern」,一樣被忽略。
  • 內建工具名會隨 VS Code 版本改名(例如終端機工具,舊文件或舊版可能寫 runCommands,新版選單顯示 execute)。照著舊教材手打,就可能打到一個已不存在的名字。

📐還有第三道牆,只是它不在你的檔案裡

你跑 T4-pytest 時若看到 Run command? / Allow / Skip 的確認框,那是執行期的人工關卡——不是你在 .agent.md 裡設的,是宿主預設就有的。它跟前兩道牆都不同:按 Skip 之後 agent 不會停下來,而是去想別的辦法(換個指令、換條路、或乾脆略過那一步繼續)。

所以它擋得住「這一次執行」,擋不住「這個意圖」。M10 的 handoff 按鈕是同一種機制,但那是你設計出來的人工關卡,位置和時機由你決定。

三個最常見的錯誤

  • 別把 SOP 抄進 agent:一旦把「怎麼做」複製進 .agent.md,就跟 Skill 重複、日後兩邊不同步——正是 M1 警告過的反例。Agent 裡只放路由,不放步驟。

  • Custom Agent 不是 selection 正確性的保證:路由規則是強力行為準則,但 description 對比句(M6 / M7 寫的)還是要寫好——疊加才有穩定行為。
🔑一句話帶走:三個槓桿疊加,不是三選一

description 對比句(M6 / M7,收「哪個 Skill 被選中」)、路由指令(🪧,收「這個角色怎麼編排」)、工具邊界(🧱,就算路由漂了,傷害也被限制住)。

v2 · Subagent:把繁雜的工作派出去,把危險的工具一起帶走

Custom Agent 可以把一部分工作派給另一個 custom agent 當 subagent 執行:subagent 在自己的 context 裡跑完整個 agentic loop,只把結果摘要回傳給呼叫者;而且它帶自己的 tools 白名單。

🔑下放的價值,在於下放的同時把權限削小

把 wbs-generator 放進 wbs-builder subagent,@meeting-ops 的 tools 就可以拿掉 execute。但這只完成一半——如果把整類 execute 原封不動搬過去,你只是換了持有人,沒換權限。

真正的收緊在於:wbs-generator 只需要「跑一支 Python」,所以 wbs-builder 展開 execute 後只勾 runInTerminal 這一項,runTask、runTests、createAndRunTask、killTerminal 全部不給。這三件事要一起做,這一步才算數:

  1. 把需要危險工具的那段工作獨立成一個 subagent
  2. 呼叫者的 tools 拿掉該工具
  3. subagent 只勾那段工作實際用得到的子工具

三個好處:context 不被汙染(看得到)、入口 agent 不再握有終端機(看不到但更重要)、爆炸半徑縮到「一個只會拆 WBS 的 agent × 一項子工具」。M11 一個會寫入外部系統的 Skill,靠的正是終端機——v1 那種配置等於把鑰匙放在最常被叫用的 agent 身上。

被呼叫的那一方:誰能把你拉去當 subagent?

一個常見誤解:「我的 .agent.md 裡沒寫 agents 欄位,所以沒有人可以呼叫到我」——方向反了。agents 欄位是寫在呼叫者身上的允許清單,不是寫在被呼叫者身上的門禁。

⚠️預設值是開放的

只要你沒有主動設 disable-model-invocation: true,你的 agent 就預設可以被任何有 agent tool、且把它列進自己 agents 陣列(或用 *)的 coordinator 當成 subagent 呼叫。

你想要的結果該怎麼設設在誰身上
可以被任何 coordinator 呼叫(預設)什麼都不用寫—
完全不能被當 subagent,只能 @ 或按鈕叫disable-model-invocation: true自己的 .agent.md
平常鎖死,但某個信任的 coordinator 仍可呼叫自己設 disable-model-invocation: true,coordinator 的 agents 陣列明確列出你的名字兩邊都要設

最後一列:被明確列進 agents 陣列,會覆蓋它自己的 disable-model-invocation: true——「預設鎖死、對信任對象開白名單」,跟 tools 白名單同一種精神,只是防的方向不同:tools 防「meeting-ops 能碰什麼工具」,這裡防「某個 agent 會不會被別人拉去用」。

這也是 M9 ② 預告的那一刻:wbs-builder 會被模型選中,所以它的 description 要寫給模型看——做什麼、什麼時候該交給我。

包裝既有工具的價值

M9、M10 蓋的牆都在 agent 身上:tools 白名單管「誰能碰什麼工具」,subagent 與 handoff 管「下一步誰決定」。但工具一旦放行,Skill 拿它做的事對不對,這些牆一道都管不到——wbs-builder 手上那台終端機,拿去打 Jira 呢?這一段把牆再往下蓋一層,蓋到 Skill 自己身上;你會發現這一層的兩道防呆裡,有一道是 agent 層完全碰不到的。

🔑本堂最重要的一個觀念

最穩的 scaffolding Skill,通常不是叫 LLM 純手寫,而是讓步驟去「包一個既有的決定性工具」、再疊上團隊規範與品質自檢。這裡用 datamodel-codegen 從 OpenAPI 規格產生 Pydantic model,Skill 負責「呼叫工具 + 套 router 慣例 + 自檢」。

這句話今天不用你相信——講師會把對照組投影出來:同一份規格純手刻兩次的 diff;然後你自己用包工具的 Skill 跑,看它為什麼穩。你在上半場 M3 已經看過偏離預期這個模式,只是這次換了一個層次:輕則類別命名、enum member 大小寫不一致(換一次產出,呼叫端的 Sentiment.positive 可能直接 AttributeError),重則型別本身對不上——不是格式難看那種一眼看得出來的偏離,是「兩份看起來都對,但兜不起來」的型別漂移。

適用前提:這個做法假設 OpenAPI spec 已經定案(治理委員會審過、或對外合約規格)。

edit 動的是你自己 workspace 裡的檔案,最壞情況是改壞一個檔,有 git 可以救。execute 動的是整台機器——裝套件、刪檔案、打外部 API 都在這一類底下。投資報酬差很多,時間有限就只削 execute。

但也別高估它:沒勾 runTests 攔不住 pytest,因為 runInTerminal 本來就能打任何指令。削子工具拿掉的是「額外的入口」,不是「終端機本身的能力」。真正的下一層護欄在 M11。
